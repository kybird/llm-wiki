## Case 2: execSync 임포트를 지웠더니 grep이 조용히 죽었다 — catch가 ReferenceError를 삼킴

### Error
모든 검색 쿼리에서 grep 결과가 사라지고 항상 다음만 출력됐다:

```
No direct matches found.
```

### Environment Context
- Packages: Node 24, llm-wiki 0.2.2 작업 트리
- Migration Issue: No

### Fix Code
```js
// 수정 1단계(5-1-1 커밋): qmd 호출만 execFileSync로 바꾸면서 임포트를 통째로 바꿔버림 —
const { execFileSync } = require('child_process');   // ← execSync 누락
// ... collectGrepResults의 아직 살아있는 execSync(grepCmd) 호출이 ReferenceError
// 수정: 둘 다 유지하고, grep exec 자체를 제거하는 커밋(5-1-6)에서 임포트 정리
const { execSync, execFileSync } = require('child_process');
```

### Analysis
- Root cause: grep용 `catch (e) { /* no matches */ }`가 exit code 1만 삼키려던 게
  ReferenceError까지 삼켰다 — 폭 넓은 catch가 진짜 버그를 "빈 결과"로 위장.
- Why it failed: 임포트 변경은 파일 전역의 횡단 변경인데 서브셋(5-1-1)만 고쳤다. 더 나쁜 건
  **검증이 통과했다**는 것 — hostile 쿼리 테스트는 "No direct matches"가 정상 응답이라
  부정(깨짐)과 부정(없음)을 구분 못 한다.
- How it was fixed: 무해한 알려진-히트 쿼리("lastCompiled")를 돌려 3파일 매치가 나오는지
  확인해서 발견, 커밋 amend로 바로잡음.

### Related Knowledge
- Patterns: [[always-merge-exact-matching]] — 검증은 인접 경로까지: 부정 테스트만으로 끝내지 말고
  반드시 하나의 알려진 긍정(known hit)을 함께 확인한다.

## Case 3: findstr은 UTF-8 시스템(ACP 65001)에서도 한국어 2키워드 매칭이 0건이었다

### Grounding
- Git Context: `hash:ce38d63`
- Evidence: 수정 전 `llm-wiki search "스코프 배포"` → grep "No direct matches"(findstr 경유);
  JS 스캐너 교체 후 동일 쿼리 → 5파일, npm-scoped-publishing.md 2/2 키워드 1위. 시스템
  레지스트리 ACP=65001(시스템 전역 UTF-8) 머신에서 실측.
- Confidence: 5/5

### Discovery
리뷰의 가설은 "findstr은 CP949 머신에서만 깨진다(이 머신은 우연히 안전)"였는데 틀렸다 —
**UTF-8 머신에서도 이미 0건**이었다. execSync가 거치는 cmd 컨텍스트의 코드페이지가 시스템
ACP와 다르게 결정될 수 있어, findstr의 "이 머신은 안전" 가정 자체가 성립하지 않았다.

### Analysis
- Why non-obvious: 깨진 검색이 QMD 시맨틱 결과에 가려져 보이지 않았다(2026-09-02 로그의
  91~94% 히트가 다 시맨틱이었다). 병합 구조에서 한 쪽의 침묵은 다른 쪽이 대신 채운다.
- Impact: 5-1-6(프로세스 안 라인 스캐너)은 미래의 CP949 사용자 보호가 아니라 **이 머신의
  현역 회복**이었다. 외부 grep 계열 도구의 코드페이지 동작은 환경마다 검증 전에는 믿지 않는다.
- Action taken: findstr/grep exec 전면 제거로 인코딩·셸 주입 문제를 동시에 원천 차단.
  검증은 Case 2의 교훈대로 알려진-히트 쿼리로.
