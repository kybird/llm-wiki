- Action taken: high 4 + 같은 계열 핫픽스 2(not_before UTC, findstr CP949)를 카드 없이 즉시

## Case 2: execSync 임포트를 지웠더니 grep이 조용히 죽었다 — catch가 ReferenceError를 삼킴

### Error
모든 검색 쿼리에서 grep 결과가 사라지고 항상 다음만 출력됐다:

```
No direct matches found.
```

### Environment Context
- Packages: Node 24, llm-wiki 0.2.2 작업 트리
- Migration Issue: No

### Fix Code
```js
// 수정 1단계(5-1-1 커밋): qmd 호출만 execFileSync로 바꾸면서 임포트를 통째로 바꿔버림 —
const { execFileSync } = require('child_process');   // ← execSync 누락
// ... collectGrepResults의 아직 살아있는 execSync(grepCmd) 호출이 ReferenceError
// 수정: 둘 다 유지하고, grep exec 자체를 제거하는 커밋(5-1-6)에서 임포트 정리
const { execSync, execFileSync } = require('child_process');
```

### Analysis
- Root cause: grep용 `catch (e) { /* no matches */ }`가 exit code 1만 삼키려던 게
  ReferenceError까지 삼켰다 — 폭 넓은 catch가 진짜 버그를 "빈 결과"로 위장.
- Why it failed: 임포트 변경은 파일 전역의 횡단 변경인데 서브셋(5-1-1)만 고쳤다. 더 나쁜 건
  **검증이 통과했다**는 것 — hostile 쿼리 테스트는 "No direct matches"가 정상 응답이라
  부정(깨짐)과 부정(없음)을 구분 못 한다.
- How it was fixed: 무해한 알려진-히트 쿼리("lastCompiled")를 돌려 3파일 매치가 나오는지
  확인해서 발견, 커밋 amend로 바로잡음.

### Related Knowledge
- Patterns: [[always-merge-exact-matching]] — 검증은 인접 경로까지: 부정 테스트만으로 끝내지 말고
  반드시 하나의 알려진 긍정(known hit)을 함께 확인한다.

## Case 3: findstr은 UTF-8 시스템(ACP 65001)에서도 한국어 2키워드 매칭이 0건이었다

### Grounding
- Git Context: `hash:ce38d63`
- Evidence: 수정 전 `llm-wiki search "스코프 배포"` → grep "No direct matches"(findstr 경유);
  JS 스캐너 교체 후 동일 쿼리 → 5파일, npm-scoped-publishing.md 2/2 키워드 1위. 시스템
  레지스트리 ACP=65001(시스템 전역 UTF-8) 머신에서 실측.
- Confidence: 5/5

### Discovery
리뷰의 가설은 "findstr은 CP949 머신에서만 깨진다(이 머신은 우연히 안전)"였는데 틀렸다 —
**UTF-8 머신에서도 이미 0건**이었다. execSync가 거치는 cmd 컨텍스트의 코드페이지가 시스템
ACP와 다르게 결정될 수 있어, findstr의 "이 머신은 안전" 가정 자체가 성립하지 않았다.

### Analysis
- Why non-obvious: 깨진 검색이 QMD 시맨틱 결과에 가려져 보이지 않았다(2026-09-02 로그의
  91~94% 히트가 다 시맨틱이었다). 병합 구조에서 한 쪽의 침묵은 다른 쪽이 대신 채운다.
- Impact: 5-1-6(프로세스 안 라인 스캐너)은 미래의 CP949 사용자 보호가 아니라 **이 머신의
  현역 회복**이었다. 외부 grep 계열 도구의 코드페이지 동작은 환경마다 검증 전에는 믿지 않는다.
- Action taken: findstr/grep exec 전면 제거로 인코딩·셸 주입 문제를 동시에 원천 차단.
  검증은 Case 2의 교훈대로 알려진-히트 쿼리로.

## Case 4: 하네스 네이티브 todo는 PreToolUse 훅으로 가로챌 수 있다 — TodoWrite 캡처 조사(카드 종결)

### Grounding
- Evidence: ① 이 세션 실측 — example-plugin(zcode-plugins-official)의 PreToolUse 훅
  (matcher `Bash|Write|Edit`)이 세션의 모든 Bash/Write 호출에 발화(도구 결과마다
  "[Hook additional context]" 주입 확인). ② 공식 샘플 훅 pre-tool-use.mjs의 smoke test
  주석이 stdin 계약 명시: `{"hook_event_name":"PreToolUse","tool_name":"…",
  "tool_input":{…}}` — tool_input에 도구 인자 전체가 담긴다. ③ Claude Code 커뮤니티
  실측(GitHub anthropics/claude-code#6975, 50+ 회 테스트): matcher `TodoWrite`가
  발화하며 stdin에 `parameters.todos` 배열(content/status/activeForm) 수신 — 단 공식
  문서에 미기재, 이슈는 closed-as-not-planned(커뮤니티 보고 등급).
- Confidence: 4/5 — ZCode에서 TodoWrite **직접** 발화는 미실증(아래 Analysis 참조)

### Discovery
카드 "TodoWrite 캡처 조사"(미결 #4)의 질문: Claude Code 등 하네스의 네이티브 todo를 훅으로
가로챌 수 있는가? **가능하다.** 방법: PreToolUse 이벤트에 matcher `TodoWrite`를 건 process
훅이 stdin JSON(`tool_name` + `tool_input.todos`)을 파일로 append하면 된다(Claude Code는
`parameters.todos`, ZCode는 `tool_input` 필드명 — 세션에서 계약 확인된 쪽은 후자).

### Analysis
- Why non-obvious: 미들세션에 워크스페이스 `.zcode/config.json` 훅을 추가해 TodoWrite를
  호출해 봤으나 **발화 안 함** — 설정 파일 훅은 세션 시작 시 로드되는 것으로 추정(발화
  불가와 구분 불가). example-plugin의 matcher `Bash|Write|Edit`가 TodoWrite에 안 걸린 건
  매처가 앵커드(전체 일치)라서 그런 것으로 보임 — 즉 "안 된다"가 아니라 "이 세션에서는
  못 확인했다"이다. 새 세션 시작 전 프로브 설치로만 확증 가능(잔여: 아래).
- Impact: 칸반 대신 하네스 네이티브 todo를 쓰는 세션도 훅 한 줄로 `doc/kanban` 부수
  활동(activity.jsonl)에 줄세울 수 있다 — 다만 ZCode 확증 전에는 Claude Code 한정 주장.
- Action taken: 카드 AC("가능 여부와 방법 문서화") 충족으로 종결. ZCode 직접 확증은
  새 세션에서 `.zcode/config.json` 프로브를 미리 심는 것으로 별도 확인 가능(카드 재발행
  사유는 아님 — 방법 문서화가 AC였음).
