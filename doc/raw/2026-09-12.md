# 2026-09-12

## Case 1: Windows 파이프 stdout은 비동기다 — 종료가 쓰기를 앞지르면 한 줄이 통째로 사라진다

### Grounding
- Git Context: `hash:16e7eb9` (수습 포함 커밋 — lib/kanban-wait.js finish)
- Evidence: bash 파이프 프로브(`node … | cat > piped.txt`)에서 auto-update 배너를 t≈0에 출력하고 3초 뒤 타임아웃 exit한 자식의 stdout이 **완전히 빈 파일**로 도착. 단독 node spawn 실험에서는 재현이 불안정(도착하기도 함) — 조건이 로드·타이밍에 의존한다는 뜻. Node 공식 문서가 플랫폼별 동기/비동기를 명시: 파일·POSIX 파이프=동기, **Windows 파이프=비동기**
- Confidence: 4/5 (유실 실측은 확실하나 정확한 소실 조건은 못 좁힘 — 재현 불안정)

### Discovery
`llm-wiki wait` 구현 중: 타이머(fs.watch/setInterval 콜백) 안에서 이벤트 한 줄을 출력하고 프로세스를 끝내면, 그 줄이 파이프 너머 호출자에게 가끔 도착하지 않는다. 이 명령의 계약(0=이벤트 한 줄, 2=침묵)에서는 "이벤트를 감지했는데 호출자가 못 받는" 상태 = 계약 위반이다.

### Environment Context
- Packages: Node v24.14.1, Windows 10 (10.0.26200), Git Bash 파이프·node spawn 파이프 둘 다 관찰
- Migration Issue: No

### Analysis
- Why non-obvious: 증상이 "가끔 전량 유실"(배너+이벤트 모두 소실)로 나타나고, 같은 코드가 통과하기도 해서(미니 재현 테스트는 통과) 결함이 CLI가 아니라 테스트에 있는 것처럼 위장했다(Case 2와 겹쳐 디버깅이 꼬임). TTY·리다이렉트 파일에서는 동기 쓰기라 재현 자체가 안 된다.
- Impact: 종료 코드가 계약인 모든 에이전트 CLI에서 동일 계열 — 특히 대기 후 한 줄만 찍고 끝나는 wait류 명령. doc/raw/2026-09-09.md Case 5(process.exit가 finally를 우회해 락 누출)의 형제: process.exit는 큐에 있는 일을 기다려주지 않는다.
- Action taken: 출력은 `process.stdout.write(줄, () => process.exit(코드))` — 쓰기 완료 콜백에서 종료한다. 콜백 미도차를 대비해 exitCode도 선심입(lib/kanban-wait.js finish).

- Concepts: [[agent-cli-contract]]
- Patterns: [[flush-before-exit]] (신규 후보 — 오늘 승격)
- **Anti-Patterns**: [[콜백 없는 출력 후 즉시 exit]]

## Case 2: 게터 반환 객체를 구조 분해하면 그 순간의 스냅샷 원시값이 복사된다 — "CLI가 출력을 잃었다"로 위장한 테스트 버그

### Grounding
- Git Context: `hash:16e7eb9` (수습 포함)
- Evidence: test/kanban-wait.test.js — spawnWait가 `{ child, get out() { return out; } }`를 반환, 호출부가 `const { child, out } = b.spawnWait(args)`로 받아 assert. 자식의 종료 코드·종료 시각은 전부 정확했는데 out만 계속 빈 문자열
- Confidence: 5/5 (원인 직접 확인, 수정 후 전량 통과)

### Error
node --test 실패 원문 2종(비동기 spawn 테스트):

AssertionError [ERR_ASSERTION]: 그 이벤트를 출력해야 한다:

SyntaxError: Unexpected end of JSON input
    at JSON.parse (<anonymous>)

### Environment Context
- Packages: Node v24.14.1, node:test 러너
- Migration Issue: No

### Fix Code
// 전(스냅샷 버그 — out은 spawn 직후의 빈 문자열로 복사되고 이후 갱신 안 됨):
const { child, out } = b.spawnWait(args);
// …await exitOf(child)…
assert.ok(out.includes('도착한 판정'));

// 후(속성 접근 — 게터가 접근 시점에 평가):
const w = b.spawnWait(args);
const code = await exitOf(w.child);
assert.ok(w.out.includes('도착한 판정'));

### Analysis
- Root cause: 구조 분해는 게터 프로퍼티를 **그 시점에 평가**해 원시값(string)을 복사한다. 이후 'data' 이벤트가 클로저의 out을 갱신해도 복사본은 영영 빈 문자열이다.
- Why it failed: 살아있는 값을 받았다고 착각하게 만드는 문법 — 객체 그대로 쓰면(w.out) 게터가 지연 평가되는데, 분해는 평가 시점을 앞당긴다. assert 메시지에 `${out}`을 심어도 빈 값이라 단서가 없었다.
- How it was fixed: 게터를 포함한 반환값은 구조 분해하지 않고 객체 속성으로 접근. spawnWait 정의에 주석으로 함정 문서화.
- 디버깅 비용: Case 1과 겹쳐 보임 — CLI측 가설(exit 자연 종료 유실 → 콜백 종료로 교정)과 테스트측 가설(게터 분해)을 이분법으로 갈라 4번의 실행(run)으로 분리했다. CLI측 교정은 Case 1 근거로 독립적으로 정당(유실 실측 있음).

### Related Knowledge
- Concepts: [[agent-cli-contract]] (assert 메시지에 실측값 심기 원칙이 진단 열쇠)
- Patterns: [[write-validation-matches-read-semantics]] (쓰는 쪽 검증이 읽는 쪽 의미와 어긋나면 조용히 빗나간다는 계열)
- **Anti-Patterns**: [[게터 반환 객체의 구조 분해]]

## Case 3: wait는 auto-update 트리거에서 제외 — stdout "이벤트 한 줄 or 침묵" 계약이 배너보다 우선한다

### Grounding
- Git Context: `hash:16e7eb9`
- Evidence: wait를 트리거 목록에 넣은 초안에서 타임아웃 테스트(2=아무것도 출력하지 않음)의 stdout에 실제로 배너가 찍힘: `llm-wiki v0.2.3: npm 업데이트 자동 반영 — 사본 갱신 updated 0 · copied 16 (상세: llm-wiki init --check)`
- Confidence: 5/5 (위반 실측 후 제외로 전량 통과)

### Design Decision
`llm-wiki wait`를 maybeAutoUpdate(bin/llm-wiki.js)의 트리거 목록에 넣지 않는다. wait의 stdout은 계약 그 자체다 — 종료 코드 0이면 이벤트 한 줄(`--json`이면 JSON 한 줄), 2면 완전 침묵. 호출자는 stdout을 파싱하고 재무장 여부를 종료 코드로 판단한다.

### Alternatives Considered
- Option A: 목록에 포함 — 거부. 어떤 명령이든 앞에 붙는 배너 한 줄이 두 계약(한 줄 전용·침묵)을 동시에 깬다. `--json` 호출자의 JSON.parse(stdout)도 깨진다.
- Option B: wait일 때만 배너를 stderr로 우회 — 거부. maybeAutoUpdate 공용 경로를 명령별 분기로 갈라엎고, "조용한 no-op 금지" 규칙(agent-cli-contract)의 단일성을 해친다.
- Selected: 제외. 백그라운드 관측 명령은 리포를 쓰지 않으니 동기화를 몰고 올 이유가 없고, 무인 루프의 능동 명령(pick/done/board)이 어차피 매 사이클 발동시킨다.

### Decision Code
// bin/llm-wiki.js — wait는 의도적으로 빠져 있다
if (['search', 'compile', 'lint', 'skills', 'board', 'card', 'pick', 'handoff',
  'done', 'supersede', 'abandon', 'reopen', 'resume'].includes(subcommand)) {
  maybeAutoUpdate();
}

### Analysis
- Context: wait 개발(16e7eb9) 중 트리거 목록 포함 시도 → 타임아웃 침묵 계약 위반 실측. wait가 doc/kanban을 읽긴 하지만 "리포를 실제로 쓰는"(부수 효과를 정당화할 만한) 명령은 아니다.
- **Trade-offs**: Complexity vs 일관성 — 예외 하나를 두는 대신 stdout 계약의 단순성을 지킨다. 갱신 전파 속도는 밤샘 루프에서 사실상 동일(능동 명령이 매 사이클 발동).
- Reversibility: High — 목록 한 줄이면 되돌린다.

### Related Knowledge
- Concepts: [[agent-cli-contract]]
- Patterns: [[one-line-stdout-contract]] (신규 후보 — wait의 0/2/130 계약, README·--help에 문서화됨)
- **Anti-Patterns**: [[계약 있는 stdout에 배너 섞기]]

## Case 4: 부작용 있는 명령을 옵션 확인용으로 실행했다 — `pick --help`가 카드를 집었고, 첫 사고 기록을 읽고도 다음 세션이 반복했다

### Grounding
- Git Context: `hash:864bc67` (가드) — 사고 자체는 2026-09-11, 2026-09-12 두 번
- Evidence: 에이전트가 옵션을 확인하려고 `llm-wiki pick --help`를 실행. `--help`는 서브커맨드 자리에서만 처리돼 `pick`이 실제로 돌았고, 엉뚱한 카드에 클레임이 찍혀 handoff로 반납해야 했다. **두 번째 사고는 첫 사고가 REVIEW 카드에 기록된 뒤에 났다.**
- Confidence: 5/5 (두 번 실측, 가드 도입 후 임시 보드에서 재현 불가 확인)

### Discovery
`--help`는 "무해한 조회"라는 보편적 관례다. 에이전트는 그 관례를 전제로 부작용 있는 명령에 붙인다. llm-wiki는 버그가 없었다 — `--help`를 모르는 플래그로 무시하고 지시대로 카드를 집었을 뿐이다. **도구가 옳게 동작해도 사고는 난다**는 것이 이 케이스의 핵심이다.

### Environment Context
- Packages: @kybird/llm-wiki 0.2.2 (전역 설치), sugarScan 실보드
- Migration Issue: No

### Fix Code
// bin/llm-wiki.js — args 계산 직후, maybeAutoUpdate·스위치 디스패치보다 앞
const KNOWN_SUBCOMMANDS = ['search', 'compile', 'lint', 'init', 'skills', 'board', 'card',
  'pick', 'handoff', 'done', 'supersede', 'abandon', 'reopen', 'resume', 'wait'];
if (KNOWN_SUBCOMMANDS.includes(subcommand) && (args.includes('--help') || args.includes('-h'))) {
  const usageKey = subcommand === 'card' && ['new', 'show', 'edit'].includes(args[0]) ? `card ${args[0]}` : subcommand;
  const usage = kanbanCmd.USAGE[usageKey];
  if (usage) console.log(usage);
  else printUsage();
  return;   // process.exit이 아니라 자연 종료 — Case 1의 교훈
}

### Analysis
- Root cause: 부작용 있는 명령에 **안전한 탐색 경로가 없었다.** 옵션을 알아내는 유일한 방법이 실행이었다.
- Why it failed twice: 기록은 재발을 막지 못했다. 첫 사고를 REVIEW 카드로 남겼는데 다음 세션이 같은 짓을 했다 — 읽은 기록보다 `--help`는 무해하다는 사전 관례가 강했다. **문서로 고칠 수 없는 것은 도구로 고쳐야 한다**는 신호다.
- How it was fixed: 가드를 디스패치보다 앞, 부작용 코드에 닿기 전에 둔다. 15개 알려진 서브커맨드 전부, args **어느 위치**에 있어도 발동. `card`는 하위 분기(new/show/edit)까지 각자의 사용법으로 덮는다 — `card new --help`가 "--help"라는 제목의 카드를 만드는 것이 최악의 경우였다.
- 사용법 문자열은 `lib/kanban-cmd.js`의 `USAGE` 맵 한 곳 — fail(인자 오류)과 가드가 같은 문자열을 쓴다. 두 군데로 갈라지면 어느 한쪽만 갱신돼 거짓 사용법을 가르친다.
- 남은 틈(리뷰 확인, 수정 불요): 플래그의 **값**이 정확히 `--help`면 가드가 문다(`card edit "X" --note "--help"` → 사용법 출력, 종료 0). 가드가 없었어도 parseArgs가 플래그로 읽어 종료 1로 거부했을 자리라 **보드는 어느 쪽이든 안 바뀐다.** 값으로 넘기려면 `--note=--help` 등호 형식.

- Concepts: [[agent-cli-contract]] — 에이전트가 1차 사용자인 CLI의 계약 계열
- **Anti-Patterns**: [[probing-side-effect-commands]]

## Case 5: 존재하지 않는 플래그를 검증 없이 위임 프롬프트에 넣었고, 받은 쪽이 그대로 실행했다 — `--card`는 무시돼 다른 카드가 집혔다

### Grounding
- Git Context: `hash:6c5e0f2` (일곱 명령 플래그 검증) · `hash:f3fcca8` (`pick --card` 실제 구현)
- Evidence: 위임 프롬프트에 `llm-wiki pick --card "<제목>"`이 들어갔다. 당시 `pick`에 `--card`는 없었다. `pick`은 `flags.claim`만 읽었고 모르는 키를 검증하지 않아 `--card`를 조용히 버린 뒤 **ordinal 최저 카드를 집었다.** 받은 쪽은 지목한 카드를 집었다고 믿었다.
- Confidence: 5/5 (원인 직접 확인, 검증 도입 후 `✗ 모르는 플래그: --card` 실측)

### Discovery
`card new`/`card edit`은 2026-09-10부터 `validateFlags`로 모르는 플래그를 거부했는데(Case 1, 2026-09-10), 카드를 **집고 끝내는** 일곱 명령(pick·handoff·done·supersede·abandon·reopen·resume)은 그 벽 밖에 있었다. [[agent-cli-contract]]이 "잔여 갭"으로 지목했던 바로 그 자리다 — `pick --claime` 오타가 unnamed-agent로 조용히 귀속된다고 적혀 있었다.

### Environment Context
- Packages: @kybird/llm-wiki 0.2.2, 에이전트 간 위임(프롬프트 전달)
- Migration Issue: No

### Fix Code
// lib/kanban-cmd.js — spec은 코드가 지금 실제로 읽는 플래그만 담는다
const PICK_FLAGS = { claim: 'string', card: 'string' };
const HANDOFF_FLAGS = { question: 'string' };
const DONE_FLAGS = { result: 'string' };
const SUPERSEDE_FLAGS = { by: 'string' };
const ABANDON_FLAGS = { reason: 'string', 'no-raw-log': 'flag' };
const REOPEN_FLAGS = { why: 'string', reason: 'string' };
const RESUME_FLAGS = { note: 'string' };
// 호출은 필수 인자 검증 직후·withLock 진입 전 — 파일을 건드리기 전에 검증

### Analysis
- Root cause 2겹: (1) **쓰는 쪽** — 존재를 확인하지 않은 플래그를 위임 프롬프트에 적었다. (2) **받는 쪽 도구** — 모르는 플래그를 조용히 버리고 성공했다. 둘 중 하나만 있었어도 사고는 안 난다.
- Why non-obvious: 위임은 검증을 **건너뛰게 만드는 구조**다. 직접 실행이면 출력이 즉시 어긋난 것을 보여주지만, 프롬프트에 적힌 명령은 다른 세션·다른 맥락에서 실행돼 어긋남이 실행자에게 정상으로 보인다. 조용한 폴백(ordinal 최저)이 그럴듯한 결과를 내서 아무도 의심하지 않았다.
- How it was fixed: 두 겹 다. 일곱 명령에 `validateFlags`를 태워 모르는 플래그가 **이름을 말하고 실패**하게 했고(`✗ 모르는 플래그: --card — 쓸 수 있는 플래그: --question`), 별개로 `pick --card`를 실제로 구현했다 — 요청된 기능이 정당했기 때문이다. 없는 기능을 부르면 실패하고, 있는 기능은 게이트를 지키며 동작한다.
- **행동 변화 2건(의도)**: 값 없는 `pick --claim`(예전 `unnamed-agent` 폴백)과 값 없는 `resume --note`(예전 기본 문구 폴백)가 이제 실패한다. 오타와 구분되지 않는 조용한 폭주를 막는 것이 폴백의 편의보다 크다.
- `pick --card`는 **우선권이 아니라 지정**이다: 의존 미충족·WIP 상한·남의 살아있는 클레임·not_before 미래·status review·종결 — 하나라도 걸리면 집지 않고 이유를 출력하고 파일을 그대로 둔다(리뷰에서 여섯 경우 전부 해시 비교로 확인).
