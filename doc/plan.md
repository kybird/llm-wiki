# llm-wiki 설계 도화지

> 2026-08-12 세션 정리. 현재까지의 **설계 논의 전체**를 한 곳에 모은 문서다.
> 실행 계획이 아니라 설계 상태 기록이다.

## 이 문서를 읽는 법

각 항목에 상태를 표기한다. **섞지 않는 것이 이 문서의 목적이다** — 지난
프로젝트가 실패로 느껴진 원인이 "목적지"와 "현재"와 "제안"이 한 덩어리로
적혀 있어서, 읽는 사람이 매번 오독한 것이었다.

| 표기 | 뜻 |
|---|---|
| **[확정]** | 결정됨. 뒤집으려면 명시적으로 뒤집는다 |
| **[제안]** | 논의에서 나왔지만 아직 채택 안 됨 |
| **[미결]** | 정해야 하는데 안 정해진 것 |
| **[사실]** | 코드를 읽어서 확인한 것 |
| **[미확인]** | 확인이 필요한 것 |

# 1. 배경 — 어디서 왔고 왜 돌아왔나

## 1.1 [사실] kybird-nest에서 여기로 돌아왔다

`D:\Project\kybird-nest` — TypeScript, 3.2만 줄, 29커밋. 칸반(웹 UI, 회귀추적),
위키 하이브리드 검색(FTS5+벡터), 로컬 SQLite + 서버 싱크, `knest` CLI, MCP,
git hook, 초대코드 기반 멤버십, 5개 에이전트에 스킬 자동 동기화, Docker 배포까지
구현돼 있다.

**[확정] 참고용으로만 둔다.** 코드를 읽을 가치는 있지만 개발은 llm-wiki에서 한다.

## 1.2 [확정] 되돌아온 이유 — 지식은 파일이어야 한다

kybird-nest는 "서버가 정본"을 **위키에까지** 적용했다. 그래서 에이전트가 지식을
보려면 이 사슬이 필요하다:

```
CLI 설치 → knest link → repo join(초대코드) → 서버 기동 → wiki embed 실행
```

고리 하나만 빠지면 **그 에이전트는 다른 컨텍스트를 본다.** 지식이 레포의 md
파일이면 이 문제가 존재하지 않는다 — `git clone`이면 끝이고, 에이전트는
Read/Grep으로 그냥 읽는다. CLI도 로그인도 네트워크도 필요 없다.

`knest wiki index --out doc/wiki/`가 존재하고 스킬에 "생성물, 커밋 금지"라고
적혀 있는 것이 방향이 뒤집혔다는 증거였다 — md가 export고 DB가 정본이면
**레포에 지식이 안 들어간다.**

## 1.3 [확정] 데이터 성질별로 저장소가 다르다

한 규칙을 성질이 다른 셋에 적용한 것이 실제 오류였다.

| 데이터 | 성질 | 저장소 |
|---|---|---|
| 위키 텍스트 | 추가 위주, 사람이 읽음, 충돌 드물고 병합 가능 | **레포의 md + git** |
| 임베딩·검색색인 | md에서 **유도 가능한 캐시** | 로컬, gitignore, 동기화 안 함 |
| 칸반 카드 상태 | 순서 있는 가변 상태, 두 머신이 동시에 바꿈 | git 병합 불가 → 3장 |

임베딩이 git으로 안 되는 건 맞지만, 그게 **서버로 가야 한다는 뜻은 아니다.**
파생 캐시니까 각 머신이 md를 보고 다시 만들면 된다.

## 1.4 [확정] 확장 경로는 막히지 않는다

파일이 정본이면 나중에 팀·SaaS로 갈 때 서버가 레포를 **읽기전용으로 색인**하는
방향이 된다(GitHub이 레포에 대해 하는 일). 반대로 서버를 먼저 정본으로 두면
파일로 되돌리는 게 이번처럼 아프다.

# 2. 최종 목표 — 수렴 엔진

## 2.1 [확정] 무엇을 만드는가

**사람은 기획 루프만 돌고, 밤새 무인으로 코딩이 도는 시스템.**

Z.AI 오프피크 요금이 근거다. 사람이 자는 시간에 돌리면 같은 작업이 싸고, 그러려면
루프가 몇 시간 연속으로 사람 개입 없이 돌아야 한다. 이 제약이 설계로 내려온다:

- 사람 승인을 루프 안에 두지 않는다 (승인 대기 = 오프피크 낭비)
- 카드 하나가 막혀도 멈추지 않는다 (다음 카드로 간다)

## 2.2 [확정] 목표는 처리량이 아니라 수렴이다

**"밤새 카드 10장을 처리했다"는 목표가 아니다.**

목표는 내가 추가한 카드 한 장이 3장이 되었다가 10장이 되었다가 30장이 되었다가
다시 10장, 1장이 되어 **모든 카드가 해소되는 것**이다.

```
1 → 3 → 10 → 30 → 10 → 1 → 0
     확장(분해)      수렴(해소)
```

이게 이 시스템이 하는 일의 전부다. 나머지는 배관이다.

## 2.3 [확정] 그래서 실패 모드는 발산이다

**늘어나는 건 쉽다.** LLM은 무엇이든 하위작업 30개로 쪼갤 수 있고, 그 30개를
또 30개로 쪼갤 수 있다. 시스템이 죽는 방식은 "밤새 아무것도 못 했다"가 아니라
**"밤새 카드가 300장이 됐다"**다.

성립 조건: **분해가 유한해야 한다.** 쪼갤 때마다 결과가 엄격히 더 작고 더
구체적이어야 하고, 몇 단계 안에 "더 못 쪼갬 = 그냥 하면 됨"에 도달해야 한다.

**[미결] 발산을 무엇으로 막는가.** 깊이 제한, 분해 시점의 "정말 작아졌나" 검사,
아니면 다른 것. 정해진 바 없다.

## 2.4 [확정] 3루프의 실제 역할

| 루프 | 하는 일 |
|---|---|
| 기획 | 분해 — 카드를 더 작고 구체적인 카드로 |
| 개발 | 해소 — 더 못 쪼개는 카드를 실제로 처리 |
| QA | 수렴 강제 — 가짜 완료를 되돌림 |

**기획은 앞단에서 한 번 도는 게 아니다.** 분해가 곧 기획이고, 루프 내내 계속
돈다. 개발 카드를 하다가 "이건 셋으로 나눠야 한다"가 나오면 그게 기획 행위다.

**QA가 없으면 곡선이 가짜로 떨어진다.** 반려는 카드를 되돌려 일시적으로 늘리지만,
반려가 없으면 "대충 완료" 처리로 수렴한 것처럼 보인다.

# 3. 카드 모델

## 3.1 [확정] 카드는 세 갈래로 끝난다

`todo / doing / done` 셋으로는 부족하다.

| 종료 | 뜻 | 카드 수 |
|---|---|---|
| **완료** | 실제로 했음 | −1 |
| **대체** | 이 카드가 저 카드들이 됨. 부모는 완료가 아니라 **소멸** | −1, +N |
| **폐기** | "이 길이 아니구나". 딸린 것까지 무효 | −1 이상 |

**부모-자식이 항상 "자식이 다 끝나야 부모 완료"인 트리는 아니다.** 부모가
사라지고 자식이 그 자리를 대체하는 길이 있고, 접근 자체가 틀려서 가지 전체가
무효가 되는 길이 있다. 관계는 트리가 아니라 **이력이 있는 그래프**다.

## 3.2 [확정] 그래서 계기판은 카드 수가 아니다

폐기도 곡선을 떨어뜨린다. 30장이 1장이 됐을 때 그게 **다 끝나서인지 다
갖다버려서인지** 카드 수만으로는 구분이 안 된다.

**계기판은 완료 대 폐기의 비율이다.** 곡선이 예쁘게 떨어져도 폐기가 대부분이면
그게 진짜 경보다.

그리고 이것이 **아침에 사람이 보는 것**이다 — 카드 30장을 하나씩 리뷰하는 게
아니라 곡선의 모양과 폐기율을 본다. 리뷰가 카드 수에 비례하면 무인의 의미가
없다.

## 3.3 [확정] 폐기 카드는 지우지 않는다

**"이 길이 아니구나"가 이 시스템에서 가장 값비싼 정보다.** 다음 세션이 같은
길로 다시 들어가는 걸 막는 유일한 기록이고, 지우면 무인 루프가 밤새 같은 벽에
반복해서 부딪힌다.

그리고 이건 위키와 그대로 이어진다 — **폐기 사유가 안티패턴의 원재료다.**
`doc/wiki/antipatterns/`가 존재하는 이유가 정확히 이것이다.

## 3.4 [제안] 어휘는 이미 이 레포에 있다

llm-wiki 위키가 이미 `status: deprecated` + `superseded_by`를 쓰고,
wiki-search 스킬이 "deprecated면 superseded_by를 따라가라"고 지시한다
([skills/wiki-search/SKILL.md:20](../skills/wiki-search/SKILL.md)).

카드에 같은 어휘를 쓰면 새 개념이 필요 없고, 위키와 보드가 같은 규칙으로 읽힌다.
대체 = `superseded_by: [...]`, 폐기 = `status: abandoned` + 사유.

## 3.5 [확정] 카드 고유번호는 안 쓴다

제목이 곧 식별자다. 위키가 이미 `[[제목]]`으로 그렇게 하고 있고, 보드만 다른
규칙을 쓸 이유가 없다. 중복 제목은 안 지으면 되고, 이름을 바꾸면 참조가 깨지는
건 위키가 이미 안고 가는 문제다.

## 3.6 [미결] 저장 형태

**아직 안 정했다.** 후보와 각각의 대가:

| | 장점 | 대가 |
|---|---|---|
| 파일 하나 (상태를 섹션으로) | 에이전트가 파일 하나만 읽음. 열면 칸반으로 보임 | 카드 이동이 블록 이동이라 병합이 지저분. 파일이 커짐 |
| 파일 하나 (상태를 표의 열로) | 이동이 단어 하나 수정 → 병합 깔끔 | 사람 눈에 보드로 안 보임. 카드 본문 자리가 애매 |
| 카드당 파일 | 충돌 거의 없음. 카드가 곧 작업 문서 | **에이전트가 보드 전체를 보려면 N개를 읽거나 CLI를 불러야 함** |
| 서버 | 충돌 없음, 웹 뷰 공짜 | 1.2에서 되돌아온 이유와 정면 충돌 |

**3.1의 관계 그래프가 여기에 새 제약을 건다.** 대체·폐기·부모자식을 표현할
자리가 있어야 한다. 평평한 3섹션 보드로는 "이 카드는 셋으로 쪼개졌다"를 담을
곳이 없다. 이 조건이 붙기 전에 논의된 후보들은 재검토가 필요하다.

## 3.7 [확정] 저장 형태를 정할 때의 원칙

세 개다. 논의 중에 실제로 후보를 하나씩 죽인 기준들이다.

1. **한 작업의 상태와 내용이 다른 파일에 있으면 한쪽은 반드시 썩는다.**
   `plan.md`/`todo.md`/`done.md`를 쓰다 결국 `plan.md`만 남은 경험이 근거다.
   "보드 표 + 카드 본문 파일" 분할안이 이 기준으로 기각됐다.

2. **생성물은 갱신을 강제하는 게 없으면 썩는다.** `index.md`가 산 증거다
   (4.4 참고). 그래서 "보드는 생성된 인덱스로 두자"는 안 된다.

3. **에이전트는 파일 하나를 읽는다.** 보드 전체를 보려고 파일 N개를 읽거나
   CLI를 호출해야 하면, 그건 1.2에서 서버를 버린 이유와 **같은 종류의
   의존성**이다.

# 4. 강제 — 왜 지시는 실패하는가

## 4.1 [확정] 스킬로는 이길 수 없다

에이전트는 시스템프롬프트에 박힌 todo 도구(TodoWrite류)를 **프로젝트 스킬보다
우선한다.** 그리고 그 todo는 세션과 함께 사라진다.

이것이 파편화의 실제 출처다 — 하네스마다 자기 todo를 만들고, 그게 휘발성이니까
어떤 모델은 `plan.md`를 만들어 영속화한다. **모델이 제멋대로여서가 아니라
하네스마다 주입 지점이 달라서** 통일이 안 되는 것이다.

따라서 `skills/kanban/SKILL.md`에 "보드는 여기 있으니 이렇게 써라"라고 적는
접근은 진다. 이 판단 때문에 "스킬 하나로 며칠 굴려보자"는 안이 폐기됐다.

## 4.2 [제안] 그래서 방향은 캡처다

**에이전트에게 보드를 쓰라고 하지 않는다.** 네이티브 todo를 그대로 쓰게 두고,
훅으로 낚아채서 파일에 쓴다. 에이전트는 보드 파일의 존재를 몰라도 된다 —
지시도 준수 문제도 없다.

**[미확인] Claude Code에서 TodoWrite를 실제로 가로챌 수 있는가.** 이게 되면
코드 없이 검증 가능하다. 아직 확인 안 했다.

## 4.3 [사실] 강제 지점은 셋뿐이고 각각 대가가 있다

| | 커버 범위 | 이식성 |
|---|---|---|
| **git 훅** | 커밋 시점만 | 모든 도구 ✅ |
| **하네스 훅** (Claude Code settings.json 등) | 세션 생명주기 전체 | 도구마다 제각각 ❌ |
| **하네스를 소유** (Pi 익스텐션) | 전부 | 그 하네스에서만 |

git 훅만이 이식 가능한데 커밋할 때만 돈다 — "작업 시작할 때 보드를 갱신해라"는
거기서 못 잡는다. 이것이 하네스를 소유해야 하는 진짜 근거다.

## 4.4 [사실] 강제가 없으면 무슨 일이 생기는지 — 이 레포가 증거다

- `llm-wiki compile index`가 **어디서도 호출되지 않는다.** pre-commit 훅은
  CLAUDE.md 미러링만 한다. README의 "Periodically: use wiki-compile"이 유일한
  트리거 — 즉 사람이 기억해야 돈다.
- kybird-nest도 같았다. `ingest_queue`를 채우는 건 자동인데 **비우는 건
  `backfill done`을 손으로 치는 것뿐**이고, `wiki add --source`는 큐를 닫지
  않는다. 안내가 시키는 대로 따라도 큐는 안 줄어든다.

## 4.5 [사실] 참고 — 큐/backfill에 대한 오독 정정

kybird-nest의 `backfill`은 **기존 레포에 이 시스템을 처음 붙일 때 쓰는
마이그레이션 도구**다(`--all` 헬프와 커밋 `dfb76e0`에 명시). 무인 루프
인프라가 아니다.

문제는 그 일회성 구조가 **상시 커밋 경로에 배선돼 있다**는 것이었다 —
post-commit이 매 커밋 +1, pre-push가 20개씩 스윕. 그래서 큐가 영원히 자라고,
동기화되지 않는 큐 때문에 머신 간 중복 소화까지 생겼다.

**이 오독은 `brief.md` 0장(무인 루프 비전)이 SSOT 맨 앞에 있어서 생겼다.**
읽는 사람이 그 렌즈로 아래를 전부 읽는다. 이 문서가 상태 표기를 쓰는 이유다.

# 5. 지식(위키) — 현재 상태

## 5.1 [사실] 검색이 자주 못 찾는다 — 원인 넷

증상: 위키에 있는 지식을 검색이 못 찾는다.

### (1) 시맨틱이 결과를 내면 grep이 아예 안 돈다 — 최우선

[lib/wiki-search.js:45](../lib/wiki-search.js) — `qmdSucceeded`가 true면 grep
fallback을 건너뛴다. QMD가 유사도로 엉뚱한 문서 **하나만** 물어와도 "성공"으로
치고, 그 단어가 정확히 박혀있는 문서를 못 찾는다.

**색인 상태와 무관하게 돌고, 색인을 갱신할수록 나빠진다:**

| 색인 | QMD | grep | 결과 |
|---|---|---|---|
| 낡음 | 빈 결과 | 돎 | 정확 매칭은 나온다 |
| 싱싱함 | 뭐라도 물어옴 | **영영 안 돎** | 정확 매칭이 묻힌다 |

즉 `compile index`를 성실히 돌릴수록 재현율이 떨어진다.

**[제안] 고침:** fallback이 아니라 **항상 둘 다 돌려서 합친다.** 시맨틱은 표현이
달라도 잡고 grep은 정확한 문자열을 잡는다 — 대체재가 아니라 보완재다.

> ⚠️ **이걸 고치기 전에는 어떤 측정도 의미가 없다.** 전부 이 버그에 오염된
> 숫자다. 어휘 문제인지 색인 문제인지 구분 자체가 불가능하다.

### (2) grep에 순위가 없고 매칭 줄을 안 보여준다

[lib/wiki-search.js:76](../lib/wiki-search.js) — 키워드마다 따로 돌려 Set에
합친다. 5개 중 5개 맞는 문서와 1개만 맞는 문서가 같이 나오고, **파일명만
출력**해서 에이전트가 어느 걸 열어야 할지 모른다.

**[제안]** 매칭 키워드 수로 정렬 + 매칭된 줄 같이 출력.

### (3) 쓸 때와 찾을 때 어휘가 다르다

[skills/wiki-log/SKILL.md:31](../skills/wiki-log/SKILL.md)의 "Concept Drift
Protection"은 *기존 이름을 재사용하라*는 것뿐이고 **별칭 요구가 없다.**

**[제안]**
- frontmatter에 `aliases: [세션 끊김, token expired, 401 대신 500]` 강제
- **에러 메시지 원문 보존.** 실무 검색어는 보통 에러 메시지 붙여넣기인데,
  raw의 `### Error` 원문이 compile되며 요약되면 걸릴 문자열이 사라진다

### (4) 색인이 갱신 안 된다

4.4 참고. `compile index`를 아무도 안 부르면 최근 지식이 임베딩에 아예 없다.

### [제안] 순서

**(1) → `compile index` → 재측정 → (2)/(3).** (1)을 안 고치고 색인부터
갱신하면 오히려 나빠진다.

## 5.2 [사실] 현재 자산

CLI 827줄(`bin/` + `lib/` 5개), 스킬 4개 325줄. 실제 지능은 스킬 프롬프트에
있고 CLI는 배관이다.

```
llm-wiki search "<query>"     위키+raw 검색 (QMD 있으면 시맨틱, 없으면 grep)
llm-wiki compile list|index   raw 목록 / index.md 재생성 + QMD 동기화
llm-wiki lint                 깨진 [[링크]], 메타데이터 누락 검사
llm-wiki init                 doc/ + 스킬 + 훅 설치
```

**위키는 2장 표에서 유일하게 이미 존재하는 조각이다.**

# 6. 스킬 · 시스템프롬프트 배포

## 6.1 [확정] 서버는 필요 없다

`llm-wiki init`이 이미 패키지의 `skills/`를 `.agents/skills/`와
`.claude/skills/`로 복사한다([lib/init.js:87](../lib/init.js)). 층은 셋:

1. **패키지 스킬** — 모든 레포 공통
2. **레포 스킬** — `.agents/skills/`, git 커밋, 동료와 공유
3. **개인 오버라이드** — `*.local.md`, gitignore

갱신 규칙: **사용자가 손댄 파일은 덮어쓰지 않는다.** 파일 맨 위 마커 줄이
사라졌으면 손댄 걸로 보고 건너뛴다(init이 남의 git 훅을 안 건드리는 것과 같은
방식).

## 6.2 [제안] 배포는 npm이 아니라 git

프롬프트 오타 하나 고치려고 버전 올려 publish할 수 없다. 안 고치게 되고, 안
고치면 스킬이 썩는다.

```
llm-wiki skills add <git-url>    스킬 레포 등록
llm-wiki skills sync             pull 받아 이 레포에 설치
```

활성 목록은 **이미 있는** `llm-wiki.config.json`에 둔다:

```json
{ "skills": { "sources": ["..."], "enabled": ["wiki-search", "kanban"] } }
```

이 파일이 git에 커밋되므로 새 컴퓨터·동료 모두 같은 세트를 받는다. 프로젝트마다
"이 레포는 이 스킬들로 일한다"가 명시된다.

**받은 스킬은 레포에 복사한다**(참조 아님). 레포가 자기 완결적이어야 `clone`
한 번으로 끝나고, 참조만 하면 `sync` 안 친 사람이 다른 스킬로 일한다 — 4.1의
파편화가 재발한다.

## 6.3 [확정] 외부에서 받는 건 스킬만

**스킬은 고르는 것이고 시스템프롬프트는 합치는 것이다.** 이 차이가 전부다.

스킬은 독립 파일이라 소스가 열 개여도 나열만 하면 된다 — 순서도 우선순위도
충돌 해결도 필요 없다. 시스템프롬프트 조각은 하나로 합성해야 하고, 산문 지시의
충돌은 도구가 못 잡는다("한국어로 답해라" vs "always answer in English"는
조용히 한쪽만 먹는다).

그래서 `AGENTS.md`는 각 레포가 직접 쓰는 짧은 파일로 두고 **합성 배관을 안
만든다.** 기존 pre-commit 훅(CLAUDE.md 정본 + 미러 강제)도 손댈 게 없다.

## 6.4 [확정] AGENTS.md에 무엇을 두는가

| | AGENTS.md | 스킬 |
|---|---|---|
| 로드 | 매 세션, 항상 | 관련될 때만 |
| 비용 | 모든 세션의 컨텍스트를 영구히 | 목록에 한 줄 |
| 길이 | 짧아야 함 | 길어도 됨 |
| 여러 소스 | 합쳐야 함 → 충돌 | 나열 → 충돌 없음 |

**기준: 에이전트가 "찾아볼 생각"을 하기 전에 알아야 하는 것만 AGENTS.md.**
나머지는 전부 스킬.

## 6.5 [확정] 남의 레포를 받을 때

남의 스킬을 sync하는 건 **그 사람이 쓴 지시를 내 에이전트가 따르게 하는 것**이다.
코드가 아니라 지시라서 리뷰 없이 들어오면 알아채기 어렵다. `sync`는 자동이
아니라 명시적으로 치는 명령이어야 하고, diff를 보여주고 승인받아야 한다.

## 6.6 [제안] 스킬 선택 UI

로컬 파일을 읽어 로컬 파일에 쓰는 것뿐이라 서버가 필요 없다. 칸반 웹 뷰어를
만들면 거기 탭 하나로 붙는다 — 따로 터미널 UI를 만들면 같은 걸 두 번 만든다.

# 8. 조사한 기존 솔루션

## 8.1 Nimbalyst — 가장 가깝지만 핵심을 안 푼다

MIT, Electron 데스크톱 + 모바일, 로컬 우선. 카드가 마크다운 + frontmatter,
git 동기화, 칸반, 세션별 git worktree.

전용 폴더 `nimbalyst-local/tracker/`만 스캔하고 파일 안에서 `#type[...]` 태그
또는 `trackerStatus` frontmatter로 항목을 표시한다. 커스텀 타입은
`.nimbalyst/trackers/`의 YAML로 정의한다.

**안 푸는 것:**
- **todo 캡처.** 에이전트에게 "워크스페이스의 태스크 파일을 읽고 갱신하라"고
  지시하는 층에 머문다 — 4.1의 문제를 그대로 안고 있다
- 위키/지식 레이어 없음
- 팀 실시간 동기화는 closed-source 서버
- 앱이 중심이고 레포는 앱이 여는 대상 — "레포에 종속적인 칸반"과 방향이 반대

## 8.2 Pi — 하네스 후보

`earendil-works/pi`, MIT, TypeScript, ~54k★. Armin Ronacher + Mario Zechner.
익스텐션이 TS 모듈이고 tools/슬래시명령/단축키/**이벤트**/TUI 전체에 접근한다.
시스템프롬프트가 1000토큰 미만 + lazy skills — 6.4에서 도달한 결론과 같은 설계다.
프로바이더 중립(통합 LLM API + MCP).

**[제안] 포크가 아니라 익스텐션.** 포크하면 빠르게 움직이는 업스트림을 평생
따라가야 한다.

**그리고 역설이 하나 있다:** 파편화의 원인이 하네스를 여러 개 쓰는 것이므로,
하네스를 하나로 만들면 근본적으로 사라진다. "여러 에이전트"가 "하나의 하네스 +
여러 모델"이 된다.

**단, 파일이 바닥이어야 한다.** 파일이면 어떤 에이전트든 그냥 읽고, Pi
익스텐션은 그 위에 얹는 **강제 층**이다. 반대로 Pi 안에만 상태를 두면 다른
도구에서 아무것도 안 보인다 — 1.2에서 서버로 했던 실수의 재판이다.

## 8.3 나머지

vibe-kanban / ai-agent-board / openkanban / saltbo-agent-kanban — 전부
"카드 하나 = worktree 하나 = 에이전트 세션 하나" 오케스트레이터다.

**공통점: 아무도 지식 레이어와 3루프 승계를 안 하고, 아무도 todo 캡처를

# 9. 작업 원칙

이 세션에서 실제로 대가를 치르고 얻은 것들이다.

1. **배관을 먼저 깔지 마라.** kybird-nest가 실패로 느껴진 원인은 코드 품질이
   아니라, 만들어진 배관이 전부 **오지 않은 소비자**를 향해 있었다는 것이다.
   `ingest_queue`가 그 표본이다 — 테이블 하나가 `printf` 하나를 먹여살렸다.

2. **목적지와 현재를 같은 문서에 섞지 마라.** SSOT 맨 앞에 목적지가 있으면
   읽는 사람이 현재를 그 렌즈로 오독한다. 실제로 이번 세션에서 마이그레이션
   도구를 무인 루프 인프라로 오독하는 사고가 났다. 이 문서의 상태 표기가 그
   대책이다.

3. **성질이 다른 데이터에 같은 규칙을 적용하지 마라.** 1.3.

4. **생성물과 분할은 썩는다.** 3.7의 원칙 1·2.

5. **측정 전에 측정 도구를 고쳐라.** 5.1(1)을 안 고치고 검색 품질을 재면
   전부 오염된 숫자다.
