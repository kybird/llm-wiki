lib/auto-update.js에 selfSkewCore(순수 로직)·checkSelfSkew(결합부)·SELF_SKEW_INTERVAL_MS 추가. maybeAutoUpdate의 deps.checkSelfSkew 주입점으로 배선을 검증한다(테스트 15건 — 코어 8, 배선·옵트아웃·격리 7). 가짜 npm 심 + 임시 홈으로 실제 결합부를 종단 검증했다(실제 홈·레지스트리 무변경). README(EN·KO) 설치·업데이트 섹션. 카드: llm-wiki 자기 스큐 힌트 — npm 최신이 앞서면 한 줄 안내(무소속). 열린 제안(미구현): 정본 레포 안에서 전역 CLI가 돌면 알려주는 로컬 검사 — 네트워크가 필요 없고 레포가 출시보다 앞선 부류를 잡는 유일한 방법이지만, 사용자의 일상 워크플로에 출력을 추가하는 결정이라 남겨두었다.

**정정(같은 날, 사용자 판정)**. "설치는 하지 않는다 — 기계 전역 변경은 사용자 터미널의 몫"은 하루 만에 뒤집혔다: 자동 갱신은 설치까지(Case 5). 이 Case가 지키하는 것은 패스 밖에서 하루 1회 돈다는 배치, 실패는 조용히, 못 잡는 부류(레포가 출시보다 앞섬)뿐이다. 종결 카드 'llm-wiki 자기 스큐 힌트'는 verdict superseded.

## [2026-11-23 design] Case 5: 자동 갱신은 설치까지 — 안내만 하던 힌트를 하루 만에 교체

### Grounding
- Git Context: `hash:95d364d`(안내만 하는 선행 구현) `hash:a589cd5`(README "CLI 자신은 못 바꾼다" 문구) — 자기 갱신 구현은 이 Case와 같은 커밋
- Evidence: 사용자 반응 "자동업데이트가 기본기능일텐데 npm 최신이 앞서면 설치를 하지 않는다니?"(2026-11-23); 종결 카드 'llm-wiki 자기 스큐 힌트'의 verdict superseded; 가짜 npm 심 + 가짜 글로벌 루트 종단 검증 20/20 — 시작 줄 → 떨어진 프로세스가 `npm i -g` → 다음 명령 완료 보고, 설치 실패 보고, npm link 접션은 조용, 옵트아웃은 npm 0회, 소스 체크아웃은 조용; 실제 글로벌 설치는 검증 내내 0.13.0 무변경
- Confidence: 5/5

### 검색 단서
자동 업데이트 안 됨 · npm update -g 직접 쳐야 함 · self-update · 자기 갱신 · detached 떨어진 프로세스 · npm link 덮어쓰기 · npm root -g 실제 디렉터리 · 갱신 중 명령 한 번 실패 · 에이전트 타임아웃이 npm 죽임 · 한 프로세스에 구버전 신버전 섞임 · junction isSymbolicLink

### 상황
"안내만 하고 설치는 사용자 터미널에서"라고 구현·문서화한 것을 보고 사용자가 반문했다: 자동업데이트가 기본기능일텐데 설치를 안 한다니. 그날 새로 넣은 설계 선택이 하루 만에 교체됐다.

### 가설
- 기계 전역 변경은 도구가 조용히 하면 안 되고 사용자 터미널의 몫이다 → 기각(사용자 판정). qmd 동반 갱신(B안, 2026-11-21)이 이미 `npm i -g`를 자동으로 하는데 llm-wiki 자신만 예외일 이유가 없었다. 내가 '사용자 승인 필요'를 기본값으로 삼은 것은 이 레포의 배포 분업(에이전트는 version bump까지, publish는 사용자 터미널)을 잘못 일반화한 것이다 — 그것은 **출시**에 대한 분업이지 **설치**가 아니다.
- 패스 안에서 동기 설치하면 된다 → 기각: 설치되는 동안 살아 있는 프로세스가 절반쯤 바뀐 패키지 위에서 뒤늦은 require로 새 코드를 읽는다(한 프로세스에 구버전과 신버전이 섞인다). 선택 의존성 qmd 때문에 수 분 걸릴 수도 있어 에이전트의 타임아웃이 npm을 죽일 수 있다.
- 명령 끝까지 붙잡고 동기 설치(qmd 방식 그대로) → 기각: 같은 타임아웃-킬 위험이 남는다. 떨어진 프로세스에 맡기면 명령은 즉시 끝나고 설치는 살아남는다.
- 글로벌이면 무조건 설치 → 기각: `npm link`는 글로벌 항목이 작업 트리를 가리키는 링크라 `npm i -g`가 링크를 출시본으로 덮어써 개발 설정을 파괴한다. 소스 체크아웃·npx 캐시·레포 로컬 설치의 갱신은 git pull·npx @latest·의존성 변경이지 npm i -g가 아니다.

### 판정
레지스트리가 앞서면 **글로벌 npm root의 실제 디렉터리 설치**일 때만 그 버전을 설치한다. 설치는 인라인 스크립트(`node -e`)로 띄운 떨어진 프로세스가 한다 — 패키지 안 파일은 갱신 중 사라지므로 스크립트를 패키지에 둘 수 없다. 결과는 파일로 남기고 다음 명령이 한 번 보고한다(성공 한 줄, 실패는 수동 명령 포함). 설치 형태 판별은 `npm root -g` + lstat(링크 여부) + realpath 비교. 버전 문자열은 셸 명령에 들어가므로 엄격한 semver만 받는다. detached 뒤의 비동기 spawn 실패는 'error' 이벤트로 오므로 반드시 듣는다 — 안 들으면 잡히지 않은 예외로 명령이 죽는다.

### 조치
lib/auto-update.js: selfUpdateCore(순수 로직)·installKind·startInstall·reportSelfUpdate. 선행 구현의 안내 줄은 "설치를 시작조차 못 했을 때"의 폴백으로만 남는다. 테스트 22건(구현 전 18 실패 → 전부 통과), 가짜 npm 심 종단 검증 20/20. README(EN·KO) 설치·업데이트 섹션과 CLI 사용법을 자기 갱신 계약으로 다시 썼다 — 선행 커밋의 "CLI 자신은 못 바꾼다"는 더 이상 사실이 아니다. 카드: llm-wiki 자기 갱신(무소속). 남은 한계: 레포가 출시보다 앞선 스큐는 여전히 못 잡는다(Case 4). 교훈: 사용자가 "자동 갱신"이라 부르는 기능에 사람 손으로 막는 단계를 내가 넣을 때는 기본값으로 하지 말고 먼저 묻는다.

## [2026-11-23 error] Case 6: npm test가 진짜 질의 로그를 오염시켰다 — 로그 65줄 중 60줄이 테스트 고정 질의

### Grounding
- Git Context: `hash:710e53e`(질의 로깅 도입) `hash:89ba2de`(push 시점 — 오염된 로그가 그대로 실림) — 수리는 이 Case와 같은 커밋
- Evidence: push 직후 `git status`에 `docs/raw/search-queries.jsonl` 수정이 남음 — 추가된 5줄의 ts가 검토 겸 돌린 `npm test` 시각(2026-11-23T11:38:54Z)과 일치; `git show HEAD:docs/raw/search-queries.jsonl` 65줄 중 고정 질의("시맨틱 회귀 질의" 24·"어휘 불일치 질의" 24·"cuda 강하 질의" 12)가 60줄, 진짜 질의 5줄; 가드만 넣고 돌린 실행은 70→75줄 재현·종료 코드 1; 격리 뒤 전체 스위트를 돌린 뒤에도 로그 해시 불변
- Confidence: 5/5

### 검색 단서
npm test 뒤 git status 더러움 · search-queries.jsonl 커밋 안 됨 · 테스트 고정 질의 · 시맨틱 회귀 질의 · findDocRoot 진짜 docs · LLM_WIKI_ROOT 격리 · EPERM 현재 디렉터리 삭제 · chdir 복원 순서 · 테스트가 진짜 레포 docs를 씀

### 상황
10커밋을 push한 직후 `git status`에 `docs/raw/search-queries.jsonl`이 또 수정 상태로 남아 있었다. 이 파일은 세션 내내 "지난 세션의 검색 기록"으로 여기고 커밋에 묶어 왔다.

### 가설
- 지난 세션의 진짜 검색 기록 → 기각: 추가된 5줄의 질의가 전부 테스트 고정 문자열이고 ts가 방금 돌린 `npm test`와 일치한다.
- 다른 테스트 파일도 누수 → 기각: `search()`를 부르는 테스트는 wiki-search-qmd 하나뿐이고, 전체 스위트 뒤 docs/ 변경도 이 파일 하나다.
- 전역 CLI 탓(이 레포의 낡은 코드) → 무관: 로깅은 레포 코드에만 있고 테스트도 레포 코드를 돌린다.

### 판정
루트코즈는 **테스트와 기능이 같은 자원 해석을 공유**한 것이다. `search()`는 doc root를 인자로 받지 않고 `findDocRoot()`로 스스로 정하고, 질의 로그를 `<docRoot>/raw/search-queries.jsonl`에 쓴다. wiki-search-qmd 테스트는 로깅 도입(2026-10-15) 전부터 있던 파일이라 doc root를 격리하지 않았고, cwd가 레포 루트라 진짜 `docs/`가 잡혔다. 로깅을 넣을 때 "이 함수를 부르는 테스트가 무엇을 공유하는가"를 따지지 않은 것이 빚이다. 같은 날 자기 갱신 테스트를 쓰다가 알게 된 "loadConfig는 cwd의 설정을 먼저 읽는다"와 같은 부류다 — 스스로 자원을 찾는 함수를 테스트에서 부르면 그 함수가 찾는 경로 전부를 격리해야 한다.

### 조치
wiki-search-qmd 테스트를 임시 doc root(LLM_WIKI_ROOT) + 임시 cwd로 격리했다. 재발 가드: 파일 시작 때 진짜 로그의 바이트를 받아 두고 `test.after`에서 같은지 단언한다 — 가드만 넣고 돌려 실패하는 것을 먼저 확인한 뒤 격리를 넣었다. 함정: Windows는 현재 디렉터리 삭제를 EPERM으로 거부하므로 마무리 훅에서 cwd 복원을 rmSync 앞에 둔다. 로그에서 고정 질의 70줄을 제거해 진짜 질의 5줄만 남겼다(회수 경향 측정 데이터가 92% 노이즈였다). 카드: 질의 로그 테스트 누수(무소속). 교훈: push 전 점검에서 `npm test` 뒤의 `git status`를 본 것이 잡았다 — "테스트는 이 레포의 docs/를 건드리지 않는다"는 README의 규칙을 기계가 지금까지 지키지 않았으니, 이 가드 같은 것을 다른 자원(activity.jsonl 등)에도 두기를 검토할 것.
