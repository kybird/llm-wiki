## Case 1: 멱등 재사용의 대상은 신원까지 비교해야 한다 — kind만 보고 재사용하면 남의 프로젝트 보드를 가로챈다

### Grounding
- Git Context: `hash:0b683b9` (수습 커밋) / 결함 발생은 `hash:6428764`의 멱등 재기동
- Evidence: 사용자 실사용 접수 — 다른 레포에서 `llm-wiki monitor`를 실행했는데 전혀 다른 레포의 칸반이 떴다. 수습 후 실측: 실레포 3개가 4747(구버전)·4748(llm-wiki)·4749(sugarScan)에 각자 정착
- Confidence: 5/5

### Error
```
이미 떠 있다 — 이 모니터를 재사용한다 (멱등 재시도).
```
위 문구가 **다른 프로젝트의 포트**에서 인쇄됐다 — B 프로젝트의 monitor가 A 프로젝트의 모니터 URL을 "재사용"이라며 되돌려준 것. exit 0이라 호출자는 성공으로 판단한다.

### Environment Context
- Packages: llm-wiki 0.4.0~0.4.2, Windows 10, 포트 기본 4747 하나를 기계 전체가 공유
- Migration Issue: No

### Fix Code
```js
// probe가 보드 신원까지 돌려준다 — /api/board의 repo.docRoot.
if (found.state === 'monitor') {
  if (found.docRoot === docRoot) { reusePrint(port); return; }  // 같은 보드만 재사용
  fail(`포트 ${port}는 다른 프로젝트의 모니터가 쓰고 있다(${who}) — ...`);
}
// 기본 실행은 4747부터 10포트 워크: 빈 포트에 자기 보드, 타 프로젝트·플릿은 skip.
```

### Analysis
- Root cause: 멱등 판정이 "이 포트의 응답이 우리 종류(kanban-board)인가"만 봤다. **종류는 같고 대상이 다른** 경우(같은 CLI의 다른 프로젝트 인스턴스)를 분리하지 않았다.
- Why it failed: "멱등 재시도≠실패" 계약(agent-cli-contract)을 구현하며 재시도의 *대상 동일성*을 전제했다 — 포트는 기계 단위 자원인데 보드는 프로젝트 단위라는 축의 불일치를 못 봤다.
- How it was fixed: /api/board에 보드 신원 `repo.{docRoot, name}` 노출(이름=리포 디렉터리, doc의 부모), 재사용은 같은 docRoot만, 기본 실행은 포트 워크, `--port` 명시는 소유자 이름과 함께 실패. 신원=docRoot라 워크트리 보드 통합과 맞물려 링크 워크트리 몇 개든 같은 프로젝트로 재사용된다.

### Related Knowledge
- Concepts: [[agent-cli-contract]] (멱등 재시도 계약의 대상 식별 조건)
- Patterns: [[question-timing-follows-answerability]]과 무관 — 링크 아님
- **Anti-Patterns**: [[종류만 보는 멱등 판정]] (신규 후보)

## Case 2: 마일스톤 모델의 종결 가드는 set/remove 쌍 경로에 모두 붙어야 한다

### Grounding
- Git Context: `hash:281d97d` (가드+--remove-milestone)
- Evidence: 이 세션 자체 사고 — 플릿 카드를 이미 종결된 '마일스톤 구현'(2/2 done)에 `--milestone`으로 묶어 "종결된 계획 아래 진행 중 카드"라는 썩은 상태를 스스로 생성. 회귀 테스트가 --remove-milestone 경로의 종결 가드 누락(종결 카드의 소속 해제가 통과)까지 포착
- Confidence: 5/5

### Error
```
종결된 마일스톤(done)에는 소속을 걸 수 없다: 마일스톤 구현 — 새 마일스톤을 만들거나 reopen으로 되돌려라.
```
(수습 후 가드 메시지. 사고 당시엔 조용히 통과했고, 자동 종결은 이미 종결된 마일스톤을 못 되돌아보므로 이 카드는 영원히 종결 계획 아래 산 채로 남을 뻔했다.)

### Environment Context
- Packages: llm-wiki 0.4.x 마일스톤 모델(plan.md 3.8)
- Migration Issue: No

### Fix Code
```js
if (kanban.TERMINAL_FOLDERS.includes(target.meta.status)) {
  fail(`종결된 마일스톤(${target.meta.status})에는 소속을 걸 수 없다: ...`);
}
// --remove-milestone 경로에도 동일한 활성 검증(쌍 경로 가드).
if (flags['remove-milestone']) {
  if (!kanban.ACTIVE_STATUSES.includes(cardObj.meta.status)) fail(`종결 카드(...)의 마일스톤은 바꾸지 않는다 — 회고 뷰가 읽는 이력이다`);
  ...
}
```

### Analysis
- Root cause: 회고 이력 보호 규칙이 "소속 걸기"에만 붙어 있었다 — 상태를 바꾸는 *모든* 경로(설정·재지정·해제)가 같은 불변식을 지켜야 하는데 하나씩 붙이다 보면 쌍이 어긋난다.
- Why it failed: 가드를 쓸 때 "이 필드를 건드리는 명령 전부"를 세지 않고 직전 사고의 경로만 막았다. 테스트가 remove 경로를 먼저 두드려서 잡혔다 — 회귀는 가드의 쌍을 검사한다.
- How it was fixed: validateMilestoneTarget에 종결 마일스톤 거부 + card edit --remove-milestone 추가(없는 소속 해제는 오타로 거부 — --remove-depends 어법) + 해제 경로 종결 가드.

## Case 3: 모니터 두 층 — 인스턴스는 프로젝트 단위, 사람 화면은 기계 단위(플릿) + 발견은 경로 등록부로

### Grounding
- Git Context: `hash:8037cce` (monitor --all)
- Evidence: `monitor --all` 실측 — 실레포 타일(llm-wiki)에서 /p/llm-wiki/ 하위 경로로 표준 보드 전체(프로젝트 라벨·마일스톤 패널) 확인. 등록부는 능동 명령·monitor 시작이 recordProject로 기록
- Confidence: 5/5

### Design Decision
1층: monitor 인스턴스는 프로젝트당 하나, 기본 포트는 4747부터 워크(같은 보드만 재사용). 2층: `monitor --all` 플릿이 기계의 모든 보드를 타일로 집계하고 `/p/<slug>/`에서 그 프로젝트의 표준 보드를 통째로 serve. 프로젝트 발견은 **기계 등록부**(`~/.llm-wiki/projects.json`) — auto-update 스탬프의 해시는 경로를 되돌릴 수 없어 경로를 직접 기록하는 등록부를 추가했다.

### Alternatives Considered
- Option A: 스탬프 해시 역산/디스크 스캔으로 프로젝트 발견 — 기각. 해시는 단방향, 스캔은 느리고 취약하다.
- Option B: 플릿이 각 프로젝트의 monitor 인스턴스에 HTTP로 물어보기 — 기각. 서버 간 통신 배관(관리 대상 인스턴스 목록·시작 순서·장애 전파)이 생긴다. 파일이 정본이므로 플릿이 doc/kanban을 직접 읽는 게 같은 계산(collectBoardAt)으로 싸게 붙는다.
- Selected: 경로 등록부 + 파일 직접 읽기. 페이지 fetch를 상대 경로로 바꿔 단일 루트와 하위 경로가 한 벌 코드로 산다.

### Decision Code
```js
// serveBoard 통합 — 단일 monitor도 플릿의 /p/<slug>/도 같은 처리기.
serveBoard(req, res, { docRoot: entry.docRoot, paths }, new URL(rest + url.search, 'http://127.0.0.1'));
// 페이지: fetch('api/board') — 선행 슬래시 없음 → 루트와 하위 경로 양쪽에서 상대 해석.
```

### Analysis
- Context: 밤에 여러 프로젝트가 루프를 돌면 아침의 사람은 기계 단위 요약을 읽는다 — URL을 프로젝트 수만큼 오가는 건 "리뷰가 카드 수에 비례하면 무인의 의미가 없다"의 포트 버전.
- **Trade-offs**: 등록부는 사실의 이차 복사(경로가 옮겨지면 죽은 항목) ↔ readProjects가 존재 검사로 걸러내고 능동 명령마다 재등록돼 자가 치유. 플릿 폴링이 등록된 전 보드를 2초마다 재계산 — 로컬 fs 읽기라 저렴, 보드 수 십 개까지 문제없음.
- Reversibility: High — 등록부·플릿 전부 유도물, 삭제해도 정본 무손상.

### Related Knowledge
- Concepts: [[agent-cli-contract]] (stdout 첫 줄 URL 계약 유지)
- Patterns: [[question-timing-follows-answerability]] (아침 화면 계열)

## Case 5: npm publish의 2FA(EOTP)는 비-TTY에서 인증 URL을 마스킹한다 — 발행 마지막 한 발은 사람 터미널이다

### Grounding
- Git Context: v0.4.1·v0.4.2 발행 시도(2026-09-17~19)
- Evidence: whoami는 `kybird`로 통과하는 세션에서도 publish는 EOTP로 실패. 비-TTY 출력:
```
npm error code EOTP
npm error This operation requires a one-time password.
npm error Open this URL in your browser to authenticate:
npm error   https://www.npmjs.com/auth/cli/******
npm error After authenticating, your token can be retrieved from:
npm error   https://registry.npmjs.org/-/v1/done?authId=***
```
URL이 `***`로 가려져 자동화(브라우저로 열기/감시자)가 불가능. 로그인 세션 유효성(whoami)과 발행 권한(OTP)은 별개다.
- Confidence: 5/5

### Error
```
npm error code EOTP
npm error This operation requires a one-time password.
```

### Environment Context
- Packages: npm 11.11.0, npm 2025-11 정책("bypass-2FA 토큰의 직접 발행 제한" — 로그인 때 notice로 확인)
- Migration Issue: No

### Fix Code
```bash
# 사람 터미널(TTY)에서:
npm publish --access public
# → 진짜 인증 URL 출력 + 대기 → 브라우저 승인 → 발행 완료
```

### Analysis
- Root cause: npm 정책이 발행에 2FA(웹 OTP)를 요구하고, 비대화형 셸에선 인증 URL을 리터럴 `***`으로 레드닥트한다 — 세션 토큰이 있어도 OTP 단계를 통과할 수 없다.
- Why it failed: "로그인됐으니 발행도 된다"는 추론이 토큰 종류별 권한(bypass-2FA 제한)을 몰랐다. 2026-09-16의 E404 위장(토큰 없음)과 같은 계열의 세 번째 발행 함정.
- How it was fixed: 발행 명령만 사람 TTY로 위임. 레지스트리 버전 폴링(npm view)으로 발행 완료를 감지해 전역 업데이트까지 자동화.

### Related Knowledge
- Concepts: [[npm-scoped-publishing]] (발행 함정 계열 — 이 컴파일에서 확장)
- **Anti-Patterns**: [[whoami 통과를 발행 권한으로 오독]] (신규 후보)

## Case 6: 값이 '--'로 시작하는 인자는 parseArgs가 플래그로 쪼갠다 — 문장형 또는 등호형으로

### Grounding
- Git Context: `hash:8037cce` 작업 중(플릿 카드 AC 기록)
- Evidence: `card edit … --ac "--all이 기계 등록부를…"` → `✗ 모르는 플래그: --all이 기계 등록부(~/.llm-wiki/projects.json — 능동 명령·monitor 시작이 recordProject로 기록)의 모든 보드를 타일로 집계한다` — 값 토큰이 '--'로 시작해 플래그로 해석됨
- Confidence: 5/5

### Error
```
✗ 모르는 플래그: --all이 기계 등록부(… — 쓸 수 있는 플래그: --goal, --plan, --ac, …
```

### Environment Context
- Packages: lib/kanban-cmd.js parseArgs(문서화된 동작: "--로 시작하는 값은 등호형으로")
- Migration Issue: No

### Fix Code
```bash
# 등호형: --ac="--all이 …"  또는 문장형: --ac "플릿(--all)이 …"
```

### Analysis
- Root cause: 설계된 동작(done --result --yes 사고 방지, 2026-09-09)이 내 텍스트에도 정확히 적용된 것 — 결함이 아니라 가드의 정상 작동을 사람이 밟은 사례.
- Why it failed: 문서화된 규칙을 쓰는 쪽이 몰랐다. 자유 텍스트(AC·result)가 대시 두 개로 시작하게 쓰지 않는 습관이 필요.
- How it was fixed: AC 문장을 "--all이"가 아닌 "플릿(--all)이"로 재작성.

### Related Knowledge
- Concepts: [[agent-cli-contract]]
