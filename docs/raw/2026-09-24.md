# 2026-09-24

## Case 1: ZCode 사용량 쿼터는 일일이 아니라 5시간 rolling window다

### Grounding
- Git Context: `hash:89f7ef3`
- Evidence: `~/.zcode/cli/log/zcode-2026-09-23.jsonl`
- Confidence: 5/5

### Discovery
쿼터 소진 시 실제 로그에 찍히는 메시지(전문 — 리셋 시각이 에러 메시지 안에 명시된다):

```
Usage limit reached for 5 hour. Your limit will reset at 2026-09-23 17:56:45
```

함께 확인된 사실 3가지:
1. **transient 429는 이미 자동 재시도된다** — 로그에 `retryReason: "rate_limited"`, provider 헤더
   `retryAfterMs`(관측 7~13분) 기반. 관측분은 전부 복구. 재시도로 못 살리는 것은 5시간 윈도우
   소진뿐 — 해당 턴은 영구 종료된다.
2. **훅(hook)으로는 쿼터 소진/복구를 잡을 수 없다** — 훅 이벤트는 SessionStart, UserPromptSubmit,
   PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, Stop, PreCompact, Notification뿐.
   Stop 훅은 정상 종료에만 붙고, 훅 스크립트는 모델 작업을 재개시킬 수도 없다.
3. **헤드리스 CLI가 없다** — `where zcode` 실패, 실행 파일은 ZCode.exe(Electron 데스크톱 앱) 단일.
   Task Scheduler 같은 외부 스케줄러가 모델 작업을 다시 굴릴 방법이 없다.

### Analysis
- Why non-obvious: "일일 쿼터"로 알고 설계하기 쉬운데 실제로는 5시간 rolling window다. 게다가
  리셋 시각이 에러 메시지에 직접 찍혀 나오므로 "죽은 뒤 최대 5시간 안에는 반드시 복구된다"는
  상한이 보장된다.
- Impact: 밤샘 무인 세션이 쿼터로 죽어도 사람 개입 없이 인계할 수 있는 시간 축의 근거가 된다.
  재개 주체는 외부 스케줄러가 아니라 **ZCode 워크스페이스 Cron 자동화**여야만 한다(모델 호출을
  수행할 수 있는 유일한 예약 실행 통로).
- Action taken: [[quota-watchdog]] 설계의 전제로 채택 — Case 2 참조.

### Related Knowledge
- Concepts: [[quota-watchdog]]
- **Anti-Patterns**: 5시간 윈도우 소진을 transient 429 재시도 로직으로 해결하려는 시도(이미
  자동 재시도되며, 윈도우 소진은 영구 종료라 재시도 대상이 아니다)

## Case 2: 쿼터 워치독 이식 — "발사 성공 자체가 쿼터 생존 신호" 프로브 원리

### Grounding
- Git Context: `hash:89f7ef3`
- Evidence: `.zcode/overnight/TASK.md`(제어 파일), ZCode 자동화 `automation-7848ae37-ccf7-4f6a-80b6-6aaadfc084df`
- Confidence: 4/5(메커니즘은 ZCode 환경에서 2026-09-24 실증 완료, 이 레포 적복은 첫 밤 관측 전)

### Design Decision
쿼터 확인용 API 호출을 만들지 않고, **주기적 자동화 발사의 성공/실패를 그대로 쿼터 프로브로
쓴다**: 쿼터 소진 중엔 발사가 모델 호출 단계에서 시작 자체가 실패(비용 0)하고 다음 주기에
재발사, 복구 후 첫 성공 발사가 제어 파일을 읽고 인계한다. 상태는 파일 2개 —
`TASK.md`(최상단 `status: inactive|running|done` 스위치 + `## resume 지침` = 인계 계약)와
`heartbeat.txt`(작업 세션이 단계마다 `YYYY-MM-DD HH:MM:SS` 한 줄 append, 마지막 줄 20분 초과 =
사망 판정). stale 판정 시 곧바로 인계하지 않고 **CLAIM append → 10분 대기 → 재확인**의 2차
방어를 둔다(사용자 아침 수동 재시작과의 경합 방지 + 20분 넘는 긴 단계의 stale 오탐 필터).
기준값 관계: **stale 20분 > 발사 주기 15분** — 원래 세션이 살아 있으면 heartbeat가 계속
갱신되므로 워치독은 절대 겹쳐 개입하지 않는다.

### Alternatives Considered
- Option A: 훅 기반 쿼터 감지 — 쿼터 소진/복구 이벤트가 없고 훅은 재개도 못 시킴(Case 1) — 기각.
- Option B: 외부 스케줄러 + 헤드리스 CLI — 헤드리스 CLI가 없음(Case 1) — 기각.
- Option C: 쿼터 조회 API를 별도 호출 — 쿼터 소진 중엔 그 호출도 죽고, 프로브 원리가 비용 0으로
  동일 정보를 줌 — 기각.
- Selected: 워크스페이스 Cron 자동화(재개 주체가 될 수 있는 유일한 통로) + 파일 기반 상태 규약.

### Decision Code
- 배치: 자동화 `automation-7848ae37-ccf7-4f6a-80b6-6aaadfc084df`, cron `*/15 21-23,0-8 * * *`
  (21:00~08:45, 15분 주기), 프롬프트는 원 명세(2026-09-24 ZCode 실증본)의 경로만 로컬화.
- 경로: `D:\Project\llm-wiki\.zcode\overnight\{TASK.md,heartbeat.txt}` — 자동화가 워크스페이스
  귀속이라 상태 파일도 같은 귀속으로. `.zcode/`는 gitignored(기계 로컬).
- 시작 절차 주입: work-loop 스킬 v11 "Overnight control file" 섹션(제어 파일 없는 소비
  워크스페이스에선 무시하는 조건부) + 루트 AGENTS.md "밤샘 작업 — 쿼터 워치독" 섹션.
- resume 지침 템플릿: 체크포인트 = 진행 중 카드 + `doc/kanban/` 활동 로그(보드가 이미 내구성
  체크포인트라 별도 파일 불요), work-loop 규칙대로 pick부터 재개.

### Analysis
- Context: 밤샘 무인 루프(work-loop)가 쿼터 소진으로 죽으면 남은 밤 전체가 날아간다(plan.md
  무인 실행 전제와 충돌). ZCode 앱이 켜져 있고 같은 워크스페이스에서 돌 때만 유효하다.
- **Trade-offs**: 평시(inactive) no-op 발사 1회당 소형 모델 호출 1회 비용 vs 사람 개입 없는
  자동 인계. CLAIM 10분 지연 vs 이중 세션 겹침 방지 — 둘 다 밤샘 맥락에서 저렴한 편.
- Reversibility: High — 자동화 삭제 + `.zcode/overnight/` 제거로 완전 철회. 스킬/AGENTS.md
  조항은 조건부라 소비 레포에 부작용 없음.
- 대안 기록: **OffPeak(闲时) 태스크는 플랜 쿼터를 소모하지 않는다**(시작 시각은 서버 결정).
  "언제 끝나도 되는" 작업은 OffPeak가 근본 해결이고, 워치독은 "오늘 밤 안에" 끝내야 하는
  작업용 — 둘은 보완 관계다.

### Related Knowledge
- Concepts: [[quota-watchdog]]
- Patterns: 파일 2개 상태 규약(스위치 파일 + 생존 신호 파일), CLAIM-재확인 2차 방어
- **Anti-Patterns**: 원 세션이 살아 있는데 heartbeat 갱신 주기보다 판정 임계값을 짧게 잡기
  (stale 임계 > 발사 주기 > 작업 heartbeat 주기 순서가 깨지면 겹침 개입한다)

## Case 3: 개발 레포의 로컬 스킬 사본은 "마지막에 실행된 llm-wiki 바이너리" 버전으로 재동기화된다

### Grounding
- Git Context: `hash:1f41ec3`
- Evidence: `.agents/skills/work-loop/SKILL.md` skill-version 추이 실측 — 세션 첫 읽기 v8 →
  `node bin/llm-wiki.js`(레포 0.5.1) 실행 후 v10 → 커밋(pre-commit 훅이 글로벌 `llm-wiki`
  0.4.2 실행, "사본 갱신 updated 4" 배너) 직후 v8로 회귀. `npm ls -g` = @kybird/llm-wiki@0.4.2.
- Confidence: 5/5

### Discovery
auto-update 사본 동기화(lib/auto-update.js)는 **실행 중인 바이너리의 패키지 루트**에서
`.agents/`·`.claude/` 사본을 끌어온다. 이 레포에선 두 바이너리가 상주한다 — 정본(0.5.1,
`node bin/llm-wiki.js`)과 글로벌 npm 설치본(0.4.2, `llm-wiki`). 버전 스탬프가 어느 쪽이든
다르면 "npm 업데이트 자동 반영"이 발동해 사본을 자기 버전으로 덮어쓴다. 따라서 **레포
바이너리와 글로벌 바이너리를 번갈아 실행하는 순간마다 로컬 사본이 v11↔v8로 플립**하고,
커밋 훅이 글로벌을 돌리므로 **커밋 한 번마다 사본이 글로벌 버전으로 회귀**한다. 세션 도중
스킬 파일 Edit가 "File has been modified since read"로 실패하는 것도 이 재동기화 때문이다.

### Analysis
- Why non-obvious: 스탬프는 마지막 동기화 버전 하나만 기록하므로 두 바이너리가 서로를
  "업데이트 필요"로 본다. git 정본 `skills/`는 절대 덮어쓰이지 않아(git이 지킴) 손실은 없고,
  맞는 것은 **세션이 실제 읽는 로컬 사본**뿐이다.
- Impact: 개발 중 스킬 편집은 정본 `skills/`에만 하고, 로컬 사본의 최신 버전 반영은
  publish + npm update(또는 수동 cp)로만 안정화된다 — 커밋 훅이 매번 되돌리기 때문.
  세션 규칙(예: 워치독 섹션)이 즉시 필요하면 AGENTS.md처럼 git 추적·상시 로드 표면에 심어야
  한다(.zcode/overnight 워치독의 시작 규칙을 AGENTS.md에 둔 근거가 이것으로 실증됨).
- Action taken: 정본 → `.agents`·`.claude` 수동 cp로 v11 재동기화. 다음 publish(0.5.2+) 후
  npm update가 글로벌을 끌어올리면 핑퐁이 소멸한다.

### Related Knowledge
- Concepts: [[quota-watchdog]], [[llm-wiki-propagation]]
- Patterns: 정본은 git이 지키고 사본은 자동 갱신이 지배한다
- **Anti-Patterns**: 로컬 사본(`.agents/`·`.claude/`)을 직접 편집해 소유권 주장하기 — 다음
  CLI 실행·커밋 훅으로 되돌려진다

## Case 4: 워치독 전파 단위 교정 — 실제 무대는 소비 레포, 운반체는 work-loop 스킬 자가등록

### Grounding
- Git Context: `hash:2a61f3f` 이후 교정 커밋
- Evidence: 사용자 교정(2026-09-24) — "llm-wiki는 다른 레포에서 사용되어 다른 레포에서
  work-loop를 돌 때 쿼터 제한을 우회하기 위한 기법". 밤샘 work-loop는 소비 레포(스탬프 기준
  10개 프로젝트)에서 돌고 쿼터 사망도 거기서 난다.
- Confidence: 5/5

### Design Decision
Case 2의 첫 이식은 정본 워크스페이스에만 자동화를 등록했다 — 자동화가 워크스페이스 귀속이라
**소비 레포엔 닿지 않는 도그푸드 실증에 불과**했다. 교정: 워치독의 동작 단위는 소비 레포
워크스페이스 각각이고, 전파 채널은 skills sync로 배달되는 **work-loop 스킬 하나뿐**(소비 레포
AGENTS.md는 시드 규약상 못 고친다). v11의 "제어 파일이 있을 때만 유지보비" 수동 규약을 v12
**자가등록 부트스트랩**으로 교정: 밤샘 실행 세션이 (a) 호스트에 예약 자동화 도구가 있고
(b) 이 워크스페이스에 워치독이 미등록이면, 스킬에 내장된 프롬프트 템플릿(`<WS>` → 워크스페이스
루트 절대경로 치환)으로 자동화 등록 + TASK.md/heartbeat 스캐폴딩을 스스로 수행한다.

### Alternatives Considered
- Option A: 정본(llm-wiki) 워크스페이스 자동화가 전 레포를 감시 — 자동화는 워크스페이스
  귀속이라 다른 레포의 죽은 세션을 살릴 수 없다 — 기각.
- Option B: CLI(예: `llm-wiki watchdog`)로 등록 지원 — 자동화 등록은 호스트 도구(ZCode
  CronCreate) 호출이라 CLI가 대신할 수 없다 — 기각.
- Option C: 소비 레포 AGENTS.md에 규칙 심기 — init은 있는 AGENTS.md를 절대 덮어쓰지 않는다
  (전파 채널 규약) — 기각.
- Selected: 스킬 자가등록 부트스트랩 — 프롬프트가 닿는 유일한 채널이자 등록 도구를 가진
  주체(밤샘 세션 자신)가 수행하는 유일한 경로.

### Decision Code
- work-loop v12 "Overnight watchdog" 섹션: 부트스트랩 4단계(도구 확인 → 중복 확인 → 템플릿
  치환 등록 → 제어 파일 스캐폴딩+.gitignore) + 운용 3단계 + 원리 + 템플릿 전문.
- 정본 등록(automation-7848ae37, D:\Project\llm-wiki\.zcode\overnight\)은 그대로 — 이 레포의
  밤샘 실행을 실제로 지키는 도그푸드 인스턴스.

### Analysis
- Context: 소비 레포의 밤샘 세션은 호스트가 ZCode(glm 에이전트)면 CronCreate를 갖고 있어
  자가등록이 가능하다; 호스트가 예약 도구가 없으면(claude 등) 섹션 전체가 무동작 — 조건부로
  무해하다.
- **Trade-offs**: 스킬에 템플릿 전문을 탑재해 분량이 늘지만 자가완결(별도 문서 의존 없음).
  워크스페이스마다 야간 no-op 발사 비용(15분×1회 소형 호출)이 새로 생긴다 — 밤샘을 실제로
  돌리는 레포에만 등록되므로 수용.
- Reversibility: High — 각 워크스페이스에서 자동화 삭제 + 섹션 무시로 철회 가능.

### Related Knowledge
- Concepts: [[quota-watchdog]], [[llm-wiki-propagation]]
- Patterns: 채널 제약이 설계를 결정한다 — 자동화 등록은 호스트 도구라 스킬(세션 프롬프트)만이
  실행 가능한 전파 경로
- **Anti-Patterns**: 도구 중심 설계(정본에 등록해두면 어딘가에 퍼지겠지) — 귀속 자원은 귀속
  단위마다 등록 주체가 있어야 한다

## Case 5: publish 유보 결정 — 스킬 단독 변경은 git 채널로 충분하다

### Grounding
- Git Context: `hash:211054e`
- Evidence: `git diff --stat 89f7ef3..HEAD -- lib bin templates` 빈 출력 실측(2026-09-24) —
  워치독 3커밋(2a61f3f·bc0c187·211054e)의 배포 표면 변경은 skills/work-loop/SKILL.md뿐
- Confidence: 5/5

### Design Decision
워치독 v12 스킬을 실은 3커밋은 push만으로 마치고 **publish를 유보**한다. 근거: 원칙 6.2(스킬
프롬프트 반복 수정은 git 채널 — publish와 분리). 소비 레포 전파는 `llm-wiki skills sync`
(git-url 등록 레포)로 충분하고, 워치독 자가등록은 순수 스킬 프롬프트 동작이라 CLI 버전이 안
올라도 동작한다. 유보 비용(의식적으로 떠안음 — [[publish-channel-separation]]):

## Case 6: 정본 워치독 해제 — 등록 주체는 이식 시점이 아니라 밤샘 시작 시점이다

### Grounding
- Git Context: `hash:780b430`
- Evidence: 사용자 요청(2026-09-24 밤) — "예약된 작업도 없는데 뭐하러 워치독을 켜놨어, 꺼라".
  inactive 상태의 no-op 발사 3회가 세션 UI에 턴으로 나타난 것이 트리거.
- Confidence: 5/5

### Design Decision
정본 워크스페이스의 도그푸드 인스턴스(automation-7848ae37)를 삭제한다. 밤샘 작업 예정이 없으면
status: inactive인 날이 계속되고 그 기간 발사는 "할 일 없음" 한 줄의 모델 호출 + 세션 UI
노이즈가 전부다. 도그푸드 가치는 이미 실증됐다(발사→프롬프트→조기 종료 경로 관측 완료).

### Alternatives Considered
- Option A: 유지(inactive no-op 감수) — 밤 21:00~09:00 15분 주기 = 매일 밤 발사 48회, 전부
  no-op — 기각.
- Option B: 제어 파일(.zcode/overnight/)까지 삭제 — 스캐폴드 재생성 낭비고 파일은 무해(자동화가
  없으면 아무도 안 읽는다) — 유지.
- Selected: 자동화만 삭제 + 문서를 실제 상태로 교정.

### Decision Code
- CronDelete automation-7848ae37; AGENTS.md "등록되어 있다" 문구 → "밤샘 시작 시에만 등록".
- 재무장 경로: work-loop v12 부트스트랩(밤샘 세션이 등록) 또는 수동 CronCreate. 소비 레포
  전파(v12 스킬)는 이와 무관하게 유지 — 그쪽은 밤샘 실행이 있을 때만 발동하는 조건부다.

### Analysis
- Context: 워치독을 "기능 이식"의 일부로 등록해버린 것이 설계 교훈 — 예약 자동화는 **발사할
  근거가 있는 기간에만** 존재해야 한다. 근거는 밤샘 작업 그 자체다.
- **Trade-offs**: 해제 비용 = 다음 밤샘 작업 시작 시 등록 절차 1회(v12 부트스트랩이 자동 수행).
  유지 비용 = 매일 밤 no-op 48회 + 사람의 주의 낭비. 비대칭이 명확하다.
- Reversibility: High — 재무장은 부트스트랩 경로로 즉시 가능.
