## Case 1: win32 CUDA 리랭커 가짜 OOM — VRAM이 12GB 남아도 "out of memory"로 하드크래시한다

### Grounding
- Git Context: `hash:713c8a2`(10-11 qmd query 전환)이 리랭커 경로를 처음 연 커밋 — 그 전엔 `qmd search`(BM25)라 리랭커를 안 탔고 크래시가 노출될 길이 없었다.
- Evidence: `Reranking N chunks... → ggml-cuda.cu:106: CUDA error → 프로세스 사망(exit 127)`, 세션 내 GPU 10시도 중 2성공. 격리 재현(node-llama-cpp 직접 구동, b10361 프리빌트): 리랭커 **단독** 6/6 성공 — **임베딩 모델 상주** 구성 11/13 크래시. 크래시 순간 `getVramState()` free **12,341MB**(used 4GB/16GB) — 진짜 메모리 부족이 아니다.
- Confidence: 5/5

### Analysis
- `ggml-cuda.cu:106`은 `ggml_cuda_error()` 안의 `GGML_ABORT` 지점(b10361 소스 대조) — 실제 실패한 CUDA 호출과 에러 문자열은 node-llama-cpp의 로그 라우팅에 가려져 표준에러에 안 나온다. 격리 스크립트에선 `[node-llama-cpp] CUDA error: out of memory`까지 포착됐다.
- 트리거는 **임베딩 모델이 CUDA에 상주한 채 리랭커 rankAll이 도는 것**(gen-only 0/6, none 0/6 vs emb-only 1/3, both 2/3~6/6) — llm-wiki `search`는 확장(generate)→임베딩→리랭크를 한 프로세스에서 전부 돌리므로 항상 이 구조다.
- qmd는 이 계열 결함을 이미 알고 있다 — `resolveSafeParallelism` 주석: *"llama.cpp CUDA on Windows is unstable with multiple simultaneous contexts (ggml-cuda.cu:98 in #519). Vulkan and CPU do not show the same failure mode"*. 단 그 수습(병렬성 1 직렬화)은 임베딩 풀에만 적용됐고 rankAll 계산 중 크래시는 JS catch 바깥(네이티브 abort)이라 qmd의 "Reranker unavailable" 강하도 안 탄다.
- **기각된 수습들(실측)**: 리랭크 컨텍스트 축소 2048/3072(5/6·3/6 크래시), `GGML_CUDA_FORCE_MMQ`(2/4), `GGML_CUDA_FORCE_CUBLAS`(4/4), node-llama-cpp 3.22.1(llama.cpp v0.5.0 — bisect 5/6, 실쿼리 2/6 크래시로 반감일 뿐). 드라이버 610.88(UMD 13.3) × 프리빌트 cublas64_13 조합 — 다른 노트북(구드라이버 추정)은 정상이라고 사용자 보고, 환경 차이가 유력.
- CPU 강제(`QMD_LLAMA_GPU=false`)는 리랭크 21청크 **650초** — llm-wiki의 120초 타임아웃에 걸려 우회 불가.

### Design Decision
llm-wiki가 고칠 수 있는 층은 호출자뿐이다 — `collectQmdResults`가 CUDA 크래시(stderr에 `CUDA error`)만 골라 **같은 수집을 `QMD_LLAMA_GPU=vulkan` 1회 강하**해 회수한다. CUDA가 안정한 기기에선 첫 시도가 통과해 비용 0, 깨진 기기도 풀 리랭크 품질의 결과를 항상 받는다(vulkan 실측 13~22초 — 타임아웃 120초 내). CUDA 자체 속도 복구는 드라이버 교체(사용자 결정)나 상류 수정을 기다려야 한다.

### Related Knowledge
- Concepts: [[qmd-optional-dependency]], [[cuda-version-coexistence]](이번 건은 다중 버전 공존이 아니다 — 툴킷 v13.3 단일, 프리빌트 cublas64_13와 일치, 로드는 성공)
- **Anti-Patterns**: "CUDA error = OOM = VRAM 부족"으로 읽기(이번 건은 free 12GB에서 발생 — TROUBLESHOOTING의 런타임 OOM 행과 같은 문자열, 다른 병), `NODE_LLAMA_CPP_GPU` 변수 착각의 재발 방지는 동일.

## Case 2: npm 0.7.0 발행 뒤 10커밋 미푸시 — "npm엔 0.7, 소스는 0.6" 불평의 정체

### Grounding
- Evidence: `git status` — local main ahead of origin/main **10커밋**(`e97de7a 0.7.0` 버전 bump·`713c8a2` query 전환 포함 전부 미푸시), npm 레지스트리는 0.7.0 발행 완료. 다른 컴퓨터에서 GitHub 소스 받으면 0.6 시절 코드.
- Confidence: 5/5

### Discovery
**발행(publish)과 푸시(push)는 독립 이벤트다** — 브라우저 승인으로 npm엔 0.7.0이 올라갔지만 원격 브랜치는 0.6 시절 마지막 푸시(ff3a946)에 멈춰 있었다. 소비 기기의 불평("npm에는 0.7인데 소스코드는 0.6")은 버그가 아니라 이 어긋남의 정확한 묘사. AGENTS.md 배포 절차에 "publish 후 push" 단언이 없어 빠졌다. `git push origin main`(ff3a946..7dbb2a3)으로 해소.
