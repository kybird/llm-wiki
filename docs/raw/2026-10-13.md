## [2026-10-13 error] Case 1: win32 CUDA 리랭커 가짜 OOM — VRAM이 12GB 남아도 "out of memory"로 하드크래시한다

### Grounding
- Git Context: `hash:713c8a2`(10-11 qmd query 전환)이 리랭커 경로를 처음 연 커밋 — 그 전엔 `qmd search`(BM25)라 리랭커를 안 탔고 크래시가 노출될 길이 없었다.
- Evidence: `Reranking N chunks... → ggml-cuda.cu:106: CUDA error → 프로세스 사망(exit 127)`, 세션 내 GPU 10시도 중 2성공. 격리 재현(node-llama-cpp 직접 구동, b10361 프리빌트): 리랭커 **단독** 6/6 성공 — **임베딩 모델 상주** 구성 11/13 크래시. 크래시 순간 `getVramState()` free **12,341MB**(used 4GB/16GB) — 진짜 메모리 부족이 아니다.
- Confidence: 5/5

### 검색 단서
CUDA error out of memory, ggml-cuda.cu:106, Reranking N chunks, 리랭커 크래시, exit 127, node-llama-cpp, VRAM 남았는데 OOM, ggml_cuda_error GGML_ABORT, QMD_LLAMA_GPU

### 상황
`Reranking N chunks...` 직후 `ggml-cuda.cu:106: CUDA error: out of memory`로 프로세스가 exit 127 사망 — 단, 크래시 순간 VRAM 여유는 12,341MB(used 4GB/16GB). 진짜 메모리 부족이 아닌 "가짜 OOM"이고 프로세스가 통째로 죽어 JS catch도 강하도 못 탄다. llm-wiki `search`(확장→임베딩→리랭크 한 프로세스)에서만 재현, 격리 리랭커는 6/6 성공.

### 가설
에러 문자열대로 VRAM 부족인가 — 기각(free 12GB). **기각된 수습들(실측)**: 리랭크 컨텍스트 축소 2048/3072(5/6·3/6 크래시), `GGML_CUDA_FORCE_MMQ`(2/4), `GGML_CUDA_FORCE_MUBLAS`(4/4), node-llama-cpp 3.22.1(llama.cpp v0.5.0 — bisect 5/6, 실쿼리 2/6 크래시로 반감일 뿐). CPU 강제(`QMD_LLAMA_GPU=false`)는 리랭크 21청크 **650초** — 120초 타임아웃에 걸려 우회 불가.

### 판정
`ggml-cuda.cu:106`은 `ggml_cuda_error()` 안의 `GGML_ABORT` 지점(b10361 소스 대조) — 실제 실패한 CUDA 호출과 문자열은 node-llama-cpp 로그 라우팅에 가려져 표준에러에 안 나온다. 트리거는 **임베딩 모델이 CUDA에 상주한 채 리랭커 rankAll이 도는 것**(gen-only 0/6, none 0/6 vs emb-only 1/3, both 2/3~6/6). qmd는 이 계열 결함을 이미 알고 있었다 — `resolveSafeParallelism` 주석: *"llama.cpp CUDA on Windows is unstable with multiple simultaneous contexts (ggml-cuda.cu:98 in #519). Vulkan and CPU do not show the same failure mode"*. 단 그 수습(병렬성 1 직렬화)은 임베딩 풀에만 적용됐고 rankAll 계산 중 크래시는 JS catch 바깥(네이티브 abort)이라 "Reranker unavailable" 강하도 못 탄다.

### 조치
llm-wiki가 고칠 수 있는 층은 호출자뿐이다 — `collectQmdResults`가 CUDA 크래시(stderr에 `CUDA error`)만 골라 **같은 수집을 `QMD_LLAMA_GPU=vulkan` 1회 강하**해 회수한다(efe4c14). CUDA가 안정한 기기에선 첫 시도 통과로 비용 0, 깨진 기기도 풀 리랭크 품질을 항상 받는다(vulkan 실측 13~22초 — 타임아웃 120초 내).

### Related Knowledge
- Concepts: [[qmd-optional-dependency]], [[cuda-version-coexistence]](이번 건은 다중 버전 공존이 아니다 — 툴킷 v13.3 단일, 프리빌트 cublas64_13와 일치, 로드는 성공)
- **Anti-Patterns**: "CUDA error = OOM = VRAM 부족"으로 읽기(이번 건은 free 12GB에서 발생 — TROUBLESHOOTING의 런타임 OOM 행과 같은 문자열, 다른 병)

## [2026-10-13 discovery] Case 2: npm 0.7.0 발행 뒤 10커밋 미푸시 — "npm엔 0.7, 소스는 0.6" 불평의 정체

### Grounding
- Evidence: `git status` — local main ahead of origin/main **10커밋**(`e97de7a 0.7.0` 버전 bump·`713c8a2` query 전환 포함 전부 미푸시), npm 레지스트리는 0.7.0 발행 완료. 다른 컴퓨터에서 GitHub 소스 받으면 0.6 시절 코드.
- Confidence: 5/5

### 검색 단서
npm엔 0.7 소스는 0.6, 버전 불평, 미푸시 커밋, ahead of origin, npm publish push, 발행 푸시 별개

### 상황
다른 기기에서 "npm에는 0.7.0인데 GitHub 소스는 0.6"이라는 불평 — 버그 리포트처럼 들리는 어긋남.

### 가설
발행 과정의 버그나 레지스트리 지연인가.

### 판정
**발행(publish)과 푸시(push)는 독립 이벤트다** — 브라우저 승인으로 npm엔 0.7.0이 올라갔지만 원격 브랜치는 0.6 시절 마지막 푸시(ff3a946)에 멈춰 있었다. 불평은 버그가 아니라 이 어긋남의 정확한 묘사. AGENTS.md 배포 절차에 "publish 후 push" 단언이 없어 빠졌다.

### 조치
`git push origin main`(ff3a946..7dbb2a3)으로 해소. 배포 절차에 push 완료 단언 추가(AGENTS.md).

## [2026-10-13 verification] Case 3: "환경/PATH 꼬임" 가설의 서브에이전트 이중 검증 — 전 변주 기각, 원인은 상류에 확정

### Grounding
- Evidence: 서브에이전트 2기 병렬(DLL 감사 + PATH 조건 실험) + 본 세션 추격 실험. 재현 스크립트(node-llama-cpp auto, 임베딩 상주 후 rankAll)로 조건×6회 씩.
- Confidence: 5/5

### 검색 단서
PATH 꼬임, DLL 섀도잉, conda Nsight, nvcudart_hybrid64, DriverStore, cmd /c MSYS 치환, MSIX PowerShell DLL 126, 크래시율 조건 실험

### 상황
"크래시니까 환경(PATH·DLL)이 꼬였겠다"는 자연스러운 의심을 기각/확정하기 위해 가능한 환경 지렛대를 전부 실험했다.

### 가설
**전 변주 기각(실측)**: (a) **PATH 구성은 무관** — minimal+툴킷(크래시 3/6) ≡ full PATH(conda 5디렉터리+Nsight+중복 포함, 3/6). conda·Nsight에 CUDA DLL 0개(전수 스캔) — DLL 선탁(섀도잉) 자체가 불가능한 머신. (b) **CUDA 13 hybrid 런타임(DriverStore) 가설 기각** — 프리빌트가 지연 해석하는 `nvcudart_hybrid64.dll`이 검색 경로 밖 DriverStore에만 존재(감사 확정) → 순수 Windows PATH로 DriverStore를 앞에 넣고 6회: BACKEND=cuda, **크래시 2/6 — 대조군과 동일**. 해석 가능해져도 크래시율 불변.

### 판정
llm-wiki가 닿는 모든 환경 지렛대(PATH 구성·DLL 해석·지연로드·툴킷 유무)는 크래시 확률에 영향이 없다. 크래시는 llama.cpp CUDA 백엔드 × 이 드라이버(610.88/WDDM) 조합의 상류 결함(다중 CUDA 컨텍스트, qmd #519 계열). 단, **툴킷 PATH는 CUDA 진입의 필요조건**(12/12 실증): 프리빌트 ggml-cuda.dll이 cublas64_13.dll을 툴킷 bin\x64에서만 해석 — 툴킷을 빼면 CUDA 로드 실패 → auto가 vulkan으로 강하, 크래시 0. 즉 툴킷 제거는 "CUDA 포기"이지 "CUDA 수습"이 아니다. 부산물 지식 2건: (a) Git Bash에서 `cmd /c`는 MSYS가 `/c`→`C:\`로 치환해 인터랙티브로 떠간다 — `cmd //c` 써야 함(배치 실험이 조용히 무효가 되는 전형). (b) MSIX(WindowsApps) PowerShell 7은 PATH 기반 DLL 검색이 막혀 bare DLL LoadLibrary가 거짓 음성(126)을 낸다 — CUDA DLL 진단은 Windows PowerShell 5.1이나 클래식 프로세스로.

### 조치
Case 1의 vulkan 강하 수습(efe4c14)이 최선으로 확정 — 환경 조작 시도 자체를 접는다. 부산물 (a)(b)는 진단 체크리스트에 반영.

### Related Knowledge
- Concepts: [[qmd-optional-dependency]], [[cuda-version-coexistence]]
- **Anti-Patterns**: "크래시니까 PATH/DLL 꼬임부터 의심하기"(이 머신은 부재 외에 꼬임이 없었고, 있는 유일한 부재를 채워도 안 나음) — 재현 스크립트로 조건 실험이 먼저다.

## [2026-10-13 design] Case 4: 정정 — 이 머신의 해법 레버는 드라이버가 아니라 prebuilt 로드성이다 (사용자 판정)

### Grounding
- Evidence: 사용자 정정 제보 + 당일 재실측. 현재 머신: 툴킷 v13.3 **단일**(8월의 11.8·12.4 공존은 그때 정리 완료), CUDA_PATH=v13.3, 드라이버 610.88(UMD 13.3; 8월 기억은 610.47 — 그 사이 갱신). 사용자 실측으로 qmd 정상 동작 확인: 전역 인덱스 1029파일·6,651벡터, llm-wiki search(시맨틱 83–90%), qmd query 완주(exit 0), qmd embed(3문서 15청크 5초 — GPU 속도).
- Confidence: 5/5 (현재 상태) / 3/5 (8월 세부는 기록·기억 기반)

### 검색 단서
드라이버 교체 필요?, prebuilt 로드성, cublas 버전 하나, CUDA 버전 공존 무해, CUDA_PATH 잔재, 일시적 OOM 분류, 다른 기기 진단

### 상황
Case 3의 "순수 CUDA 복구는 드라이버 교체뿐"이라는 서술에 대해 사용자 정정 제보 — 8월 수습 기억과 현재 상태가 다르다.

### 가설
8월 수습의 레버가 드라이버였다(610.47→13.x 갱신) — 과잉 서술이었다.

### 판정
2026-08-29 수습의 레버는 ① 런타임 DLL 정합 ② PATH 선두 배치(v13.3/bin/x64) ③ VS BuildCustomizations의 구 CUDA 11.8 .props/.targets/.xml 제거였다. 드라이버는 13.x 런타임을 자연 지원했을 뿐 **해결 수단이 아니었다**. "CUDA 버전 하나만 유지"의 실제 불변식이 다듬어졌다: **런타임 DLL(cublas 등)을 가진 버전이 하나**일 것 — nvcc 등 툴킷 잔재만 있는 공존은 prebuilt 경로에 무해(CUDA_PATH=v12.4 같은 소스빌드용 잔재도 로드에 무관). 오늘 첫 질의의 rerank 런타임 OOM 1회(여유 7.2GB)·2차 비재현은 "일시적 드라이버/VRAM 상태" 모드로 분류(사용자 판정) — "일시"의 빈도는 기기 상태에 따라 크게 달라지며, 임베딩 상주 패턴은 본 세션 재현에서 50% 빈도로 관측됐다.

### 조치
Case 3의 과잉 서술을 이 사례로 정정한다. 다른 기기 진단은 TROUBLESHOOTING.md "다른 기기 진단 체크리스트"(이날 추가)로 — 에러 메시지가 모드를 가린다. llm-wiki 경로는 efe4c14 vulkan 강하가 자동 회수한다.
