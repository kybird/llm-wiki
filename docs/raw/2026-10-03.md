# 2026-10-03

## Case 1: 0.6.0 발행 직후 npm 캐시 지연 — view·update가 수 분간 구 latest를 보여준다

### Grounding
- Git Context: `hash:924905a`
- Evidence: `npm view @kybird/llm-wiki version` → `0.4.2` vs `curl -s https://registry.npmjs.org/@kybird/llm-wiki` → `dist-tags: {'latest': '0.6.0'}` (동일 시각, 발행 수 분 후)
- Confidence: 5/5

### Verification
사용자 TTY에서 `npm publish --access public` 성공(0.6.0). 직후 검증 체인:

1. `npm view version` → **0.4.2** (발행됐는데 구버전) — npm 로컬 캐시(`_cacache` packument)가
   발행 전 메타데이터를 max-age 동안 유지. 레지스트리 원본 JSON에는 0.6.0 존재.
2. `npm install -g @kybird/llm-wiki@0.6.0` → **notarget "a package version that doesn't exist"**
   — 같은 캐시가 버전 목록 자체를 안 믿음.
3. `npm install -g @kybird/llm-wiki@0.6.0 --prefer-online` → **성공**, `npm ls -g` 0.6.0 실측.
4. 이 셸에서 `npm whoami` → `kybird` — 사용자 publish 세션의 토큰이 ~/.npmrc에 남아
   에이전트 셸도 인증 상태가 됨(비-TTY publish EOTP 한계와 별개 — 인증과 검증은 다른 단계).

전파 실측(소비 레포, 전역 0.6.0 CLI 첫 명령):
- **PocketGauage(마이그레이션 발화)**: `[doc → docs] 레이아웃 전환 완료 (git rename 스테이징
  포함 — 커밋은 사용자 몫)` + qmd 안내(`qmd collection remove pocketgauage-wiki
  pocketgauage-wiki-raw 후 llm-wiki compile index`) + 사본 갱신 updated 13. git status 141개
  rename(R100 — doc/evidence/의 png까지 intact), doc/ 소멸·docs/ 존재.
- **LossFunction(보류 경로)**: `⚠ doc→docs 마이그레이션 보류 — docs/가 이미 있다` 한 줄 후
  레거시 doc/ 폴백으로 보드 정상 — docs/ 선점 레포의 의도 동작 첫 실전 사례.

### Analysis
- Confirmed: 발행 자체는 즉시 반영되지만 **npm 클라이언트 캐시가 TTL 동안 구 latest를 서빙**한다.
  "npm update만 하면 된다" UX는 발행 직후 수 분의 맹점을 갖는다 — 소비 레포 사용자가
  "update했는데 갱신 안 됐다"로 겪을 미래 접수 포인트.
- Implications: 발행 검증·전역 업데이트는 `--prefer-online` 또는 curl(레지스트리 JSON 직접)
  로 우회한다. 감시자 패턴도 `npm view` 폴링이면 같은 지연을 먹는다 — 완화책은 폴링 간격이
  캐시 TTL보다 크거나 prefer-online.

## Case 2: spawn 테스트의 state 밀폐 누락이 등록부를 오염시켰다(재발)

### Grounding
- Git Context: `hash:c3601a3`
- Evidence: `~/.llm-wiki/projects.json`에 `C:\Users\admin\AppData\Local\Temp\kb-migrate-*` 22건
- Confidence: 5/5

### Error
잘못된 동작(에러 아님): migrate-doc-dir 테스트들이 `node bin/llm-wiki.js board`를 temp 레포에서
spawn했는데 LLM_WIKI_STATE_DIR 밀폐가 없어, board의 maybeAutoUpdate → recordProject가 실제
기계 등록부에 temp 프로젝트를 등록했다. 플릿(monitor --all)이 죽은 temp 보드들을 타일로 보게
되는 상태.

### Environment Context
- Migration Issue: No

### Fix Code
```js
// test/migrate-doc-dir.test.js — 등록부를 때리지 않게 state 디렉터리 밀폐
const STATE = fs.mkdtempSync(path.join(os.tmpdir(), 'kb-migrate-state-'));
function run(args, cwd) {
  return spawnSync(process.execPath, [BIN, ...args], {
    cwd, encoding: 'utf8', timeout: 60000,
    env: { ...process.env, LLM_WIKI_STATE_DIR: STATE },
  });
}
```
+ 등록부 수동 정리(temp 22건 삭제 → 6 실제 프로젝트) + test.after로 STATE 정리.

### Analysis
- Root cause: 2026-09-19의 등록부 오염 사고(플릿 설계 당시 교훈 — 기존 spawn
  테스트 9종은 전부 밀폐 관례를 지키고 있었다)의 **재발**. 새 테스트 파일이 관례를 몰랐던
  게 아니라 관례가 테스트 파일만 보고 문서화돼 있지 않았다.
- Why non-obvious: 테스트가 통과하고(104종) 콘솔에도 아무 소리가 없다 — 오염은 플릿 화면을
  열어봐야만 보이는 조용한 실패다.
- How it was fixed: 즉시 수습(정리+격리) + 관례의 승격 — [[tests-isolate-machine-state]]
  패턴 페이지로 문서화해 다음 테스트 작성 세션이 관례를 검색으로 만날 수 있게.
