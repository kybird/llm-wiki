# 2026-09-10

## Case 1: card edit이 무엇도 바꾸지 않았는데 "Card edited"를 보고한다 — 에이전트 CLI의 조용한 no-op 성공

### Grounding
- Git Context: `hash:cc0f4b1` (결함 존재 시점; 수정은 이날 커밋)
- Evidence: sugarScan 프로젝트 실사용 접수 — `card edit <제목> --depends "<선행 카드>"`가 성공 출력 후 git diff로 확인하기까지 "걸린 줄 알았"음. 수정: lib/kanban-cmd.js validateFlags·test/kanban-write.test.js 회귀 6종
- Confidence: 5/5

### Error
잘못된 동작(재현, 어느 카드로든):

```
llm-wiki card edit "<존재하는 카드 제목>" --nonexistent-flag "쓰레기"
→ Card edited: D:\...\카드.md      종료 코드 0      파일 변화 없음

llm-wiki card edit "<존재하는 카드 제목>" --note
→ Card edited: ...                 종료 코드 0      파일 변화 없음

llm-wiki card edit "<존재하는 카드 제목>" --depends "x"
→ Card edited: ...                 종료 코드 0      파일 변화 없음
```

올바른 출력(수정 후):

```
✗ 모르는 플래그: --nonexistent-flag — 쓸 수 있는 플래그: --goal, --plan, --ac, --add-ac, --check-ac, --note, --renew-claim, --depends, --add-depends, --remove-depends
✗ --note 에 값이 없다 — `--note "<값>"` 또는 `--note=값` 형태로 줘야 한다.
```

### Environment Context
- Packages: @kybird/llm-wiki 0.2.2 (npm link로 전역 사용 — 미커밋 작업 나무가 즉시 다른 레포(sugarScan)에 반영되는 구조)
- Migration Issue: No

### Fix Code
`validateFlags(flags, spec)` — card new/edit 공용. spec은 `{ 이름: 'string' | 'flag' }`:
모르는 키 → 이름 나열 후 실패, 'string' 플래그에 값 없음(parseArgs가 심는 `true`, 반복
플래그 배열의 원소 포함) → 실패. card edit은 변경 플래그 자체가 없으면
"바꿀 것이 지정되지 않았다"로 실패. 성공 출력은 변경 토큰을 붙인다:
`Card edited: <경로> (note +1, ac +2, depends +선행 카드)`. 플래그는 있으나 결과가
동일하면(멱등 재시도) `변경 없음 — 이미 그 상태다` 출력 후 종료 코드 0, 파일 재작성 없음.

### Analysis
- Root cause: card edit이 flags 객체에서 아는 키만 꺼내 쓰고 모르는 키는 들여다보지
  않은 채, 마지막에 조건 없이 writeCard + `console.log('Card edited: …')`. "무엇을
  바꿨는가"와 "성공했는가"가 분리돼 있지 않았다.
- Why it failed: 주 사용자가 사람이 아니라 에이전트라는 설계 전제(개선계획 §3.2)가
  검증 계층에 반영돼 있지 않았다. 에이전트는 종료 코드와 출력 문구로만 판단하므로 오타
  난 플래그 하나가 조용한 성공이 되고, 다음 단계가 "의존성을 걸었다"를 전제로 진행된다.
  지식 그래프 쪽에서 경고하는 "근거 없는 검증 기록"(always-merge-exact-matching)과
  같은 실패 형태가 CLI 계층에서 난 것 — 부분 성공(플래그 파싱)을 전체 성공(편집)으로
  취급하는 조기 분기.
- How it was fixed: 검증을 파일 쓰기 전으로 옮기고, 성공 보고를 실제 변경 내역에
  묶었다. "값이 같아서 결과적으로 안 바뀜"은 실패가 아니라 멱등 성공으로 구분 —
  후자를 실패로 만들면 재시도가 깨진다.
- How to apply: 같은 구조(플래그 조용히 무시 + 무조건 성공 출력)를 쓰는 하위 명령에
  명세 기반 검증을 공용 헬퍼로 걸어야 한다. 어디는 엄격하고 어디는 관대하면 사용자가
  규칙을 못 배운다.

### Related Knowledge
- Concepts: [[agent-cli-contract]] — CLI의 1차 사용자는 종료 코드로만 판단하는 에이전트 (모르는 플래그 거부·no-op 실패 포함)
- Patterns: [[always-merge-exact-matching]] — 부분 성공을 전체 성공으로 취급하는 조기 분기의 형제 사례
- 선행 작업: [[2026-09-09]] fcd1f4b "parseArgs 플래그 삼킴 방지·필수 플래그 'true' 기록 차단" — 같은 벽의 이전 조각

## Case 2: depends_on을 카드 생성 후에 걸 방법이 없다 — 의존성은 계획하다가 알게 된다

### Grounding
- Git Context: `hash:cc0f4b1` (결함 존재 시점)
- Evidence: card new은 --depends를 meta.depends_on에 기록(구 lib/kanban-cmd.js:135·144·157)하나 card edit에는 해당 플래그가 없었음. pick은 depends_on을 실제로 읽어 자격을 가름(구 310행·589행·614행). 수정 후 회귀: 추가·제거·전체 교체·없는 카드·자기 자신·순환·종결 의존성 허용+pick 일치·레거시 정리(임시 보드 8종, npm test 20/20)
- Confidence: 5/5

### Error
```
card new  "<제목>" --depends a,b   → meta.depends_on에 기록된다
card edit "<제목>" --depends a,b   → 그런 플래그가 없다. 무시된다. (Case 1의 조용한 성공)
```

의존성이 안 걸린 카드는 선행이 안 끝났는데도 pick에 집힌다. 실사용에서는 자유 텍스트
메모로 적어 두는 우회가 생기는데 pick은 그걸 읽지 못한다.

### Environment Context
- Packages: @kybird/llm-wiki 0.2.2
- Migration Issue: No

### Design Decision
card edit에 의존성 편집을 열되 **ac 계열이 이미 쓰는 어법**을 따른다:
`--depends a,b`(전체 교체) → `--add-depends`(합집합) → `--remove-depends`(차집합),
적용 순서는 이 순서로 결정적. 검증 규칙(card new에도 동일 적용):

1. **제목 정확히 일치**로 존재 검사 — pick의 resolved 판정이 정확한 제목만 비교하므로,
   슬러그 폴백을 허용하면 pick이 영원히 못 푸는 의존성을 검증이 만들어 준다.
2. **자기 자신·순환 거부** — 순환 판정은 **활성(cards/) 카드의 간선만** 따른다. 종결
   카드를 의존성으로 넣는 것은 허용(pick의 resolved: done/superseded는 이미 해소)되고,
   종결 카드 자신의 depends_on은 아무도 기다리지 않는 죽은 이력이라 순환을 만들지
   않는다. 종결 카드의 의존성 편집 자체는 거부.
3. **새로 들어오는 간선만 검증** — 이미 있던 의존성의 제거는 검증 없이 허용. 검증이
   없던 시절의 끊어진 의존성(대상 카드 소멸)을 정리하는 길이기 때문이다. 단 제거 대상이
   현재 목록에 없으면 오타로 보고 실패(check-ac가 없는 번호를 거부하는 것과 같은 규칙).
4. **전수 로드 1회** — 검증당 listAllCards 1회(기존 findCard 1회와 같은 비용). 락 안에서
   도니 반복 로드 금지.

### Alternatives Considered
- Option A: 순환 검사를 전체 카드(종결 포함) 간선으로 — 기각. 종결 카드를 경유하는
  경로는 pick이 기다리지 않으므로 거짓 양성만 만든다(쓰기 규칙이 읽기 규칙보다 엄격하면
  합법적인 상태를 입력할 방법이 없어진다).
- Option B: --remove-depends의 없는 대상을 멱등 성공으로 — 기각. 제거 오타가 조용한
  성공이 되면 "제거했다"를 믿고 진행한다(Case 1과 같은 형태). 제거의 멱등성은 "목록에
  있는 것의 재제거"가 아니라 "새로 걸 때 이미 있으면 변경 없음"으로 충분하다.
- Selected: 위 4규칙 — 쓰기 검증을 pick의 판정(resolved = done/superseded 폴더 존재,
  정확한 제목 비교)에 정확히 맞추는 것이 원칙.

### Decision Code
`validateDepTargets(paths, title, deps)` — deps.includes(title) 거부 → listAllCards
1회로 존재 검사 → 활성 카드만의 그래프에서 `depCyclePath`(DFS)로 title에 닿는 경로
탐색, 발견 시 `순환 의존성이다: A → C → B → A` 전체 경로를 보고 실패.

### Analysis
- Context: 선행 카드가 나중에 생기는 것이 정상 흐름인데, 유일한 기록 수단이 카드를 새로
  뜨는 것뿐이었고 그러면 Notes 저널과 이력을 잃는다.
- **Trade-offs**: 엄격한 존재 검사 vs 레거시 정리 — "새로 거는 간선만 검증"으로 둘 다
  확보. 순환 판정의 활성 간선 한정은 이론적으로 doing/review 카드가 reopen되는 경로의
  일시적 교착을 완전히 배제하지 않으나, 그는 pick이 읽는 규칙 밖 상태 전이(reopen)의
  문제라 여기서 막지 않는다.
- Reversibility: High — 카드 포맷·센티넬·Notes append-only·AC #N 안정성·renew-claim은
  전부 무변경. depends_on을 쓰는 경로만 열었다.
