# 2026-10-11

## Case 1: 종결 카드의 사후 판정 — lifecycle와 outcome이 보드에서 같은 칸을 쓰던 간극

### Grounding
- Git Context: `hash:d9423be` (verdict 명령 구현)
- Evidence: TTSTextViewer 보드 — 마일스톤 "MOSS SFT 밤샘 사이클"(멤버 5장) 2026-09-25 전원 종결로 자동 완결, 09-28 노선 자체가 기각(억양 상한은 100M LM 사전학습 병목 — SFT로 불가). 판정은 raw log·plan.md에만 존재하고 보드에는 흔적 없음. 후속 세션이 `milestone-done`을 "채택 성공"으로 오독해 사용자에게 잘못 보고.
- Confidence: 5/5

### Design Decision
도구는 계약대로 동작했다 — 버그가 아니라 **설계 간극**이다. "작업 완결(lifecycle)"과
"노선/제품 판정(outcome)"이 보드상 구분되지 않아, 종결 **뒤에 도착한** 판정을 붙일
경로가 없었다. 유일한 우회로는 `reopen`(가짜 완료 되돌리기)인데 의미가 틀리다 —
진짜로 다 한 작업에 판정만 늦게 도착한 케이스를 표현 못 한다.

해법: `llm-wiki verdict <제목> --outcome adopted|rejected|superseded --why "…"` —
**순수 부착(append-only)**.

1. 종결(done/superseded/abandoned) 카드만 대상 — 활성 카드는 거부(판정은
   `done --result`에 담는다). 상태·폴더 불변, frontmatter `outcome`/`outcome_at`
   + Result 라인 + 활동 로그(`verdict`/`milestone-verdict`).
2. 재판정은 최신이 frontmatter를 이기고 이력은 Result 라인으로 누적(감사 가능성).
   reopen/abandon/supersede 의미 불변 — 이 명령은 판정만 쓴다.
3. 자동완결 문구(마일스톤 Result 라인·`milestone-done` detail·모니터 라벨)에
   "작업 완결·판정 별도" 명시 — 오독은 데이터가 아니라 **읽는 곳**에서 나므로
   쓰는 곳과 읽는 곳 모두에 극복 문구를 심었다. 보드 ✓ 줄에도 판정 병기.
4. `board report`는 판정 붙은 마일스톤을 done 카운트에서 분리해
   adopted/rejected/superseded 집계 — outcome 필드 없는 기존 보드는 기존 스키마
   그대로(마이그레이션 불요, 하위호환).

### Analysis
- Context: plan.md 3.8의 "종결은 자동"은 lifecycle만 말했다 — outcome 축은 미정이었고
  이번 사고가 그 빈자리를 실측으로 채웠다. 3.3(폐기 기록 보존)과 같은 근거로
  판정 이력도 append-only.
- **Trade-offs**: 별도 필드 vs Result 텍스트만 — 필드가 있어야 report가 기계적으로
  분리 집계할 수 있다(생성물은 읽는 곳의 계약이 없으면 썩는다 — 3.7 원칙 2).
- 실패 경로: 활성 카드 verdict는 명확히 거부 — 조용한 성공이면 "판정 기록했다"를
  믿은 채 진행된다(validateFlags 규칙과 같은 맥락).
