## Case 1: bin의 전역 --json 선추출이 명령층 플래그 검증을 우회한다 — 폐지 플래그가 조용한 성공이 될 뻤다

### Grounding
- Git Context: `hash:5f1ac2d` (수습 포함 커밋)
- Evidence: 구현 전 subagent 설계 리뷰가 지목(블로커 ②) + `board video --json`이 실제로 exit 0으로 플래그를 무시하던 인접 결함(같은 결함군이라 같은 커밋에서 처분). 수습 후 실측: `node bin/llm-wiki.js board --html` → stderr `모르는 플래그: --html — 쓸 수 있는 플래그: ` exit 1
- Confidence: 5/5

### Error
- 예방된 결함: `board --json` 폐지 후에도 bin이 `--json`을 args에서 미리 뽑아 내므로(`rest.filter(a => a !== '--json')`) 명령의 validateFlags에 **도달하지 않는다** — 플래그 검증만 추가하면 텍스트 보드를 뿌으며 exit 0(조용한 no-op 성공).
- 실재했던 결함: `llm-wiki board video --json` → exit 0, 플래그 조용히 무시(boardVideo가 rest를 아예 검증 안 함).

### Environment Context
- Packages: llm-wiki 0.3.0 코드베이스, Node v24.14.1, Windows 10
- Migration Issue: No

### Fix Code
```js
// bin — 추출된 사실을 명령에 넘긴다(우회 금지)
case 'board':
  if (args[0] === 'video') kanbanCmd.boardVideo({ rest: args, json: jsonRequested });
  else kanbanCmd.boardView({ rest: args, json: jsonRequested });
// kanban-cmd — 명령층에서 명시 실패
const flags = { ...parseArgs(options.rest || []).flags };
if (options.json) flags.json = true;
validateFlags(flags, VIDEO_FLAGS); // spec {} — 어떤 플래그도 불허
```

### Analysis
- Root cause: 플래그 검증 계층(validateFlags)과 플래그 전처리 계층(bin의 전역 추출)이 **서로 다른 층**에 있는데, 전자가 후자가 제거한 토큰을 검증한다고 가장하고 있었다. 검증은 "사용자가 친 토큰"에 대해 이뤄져야 하는데 전역 추출이 그 토큰을 args에서 지운다.
- Why it failed: 종료 코드로만 판단하는 에이전트 호출자에게 exit 0 + 정상 출력은 "플래그가 먹혔다"와 구분 불가 — [[agent-cli-contract]]의 조용한 no-op 금지 위반이 플래그 폐지라는 변경에서 재발.
- How it was fixed: 추출된 불리언을 dispatch 너머로 넘겨 명령층에서 validateFlags 표준 경로로 실패시킴. 규칙: **전역 추출하는 플래그는 추출 사실까지 검증 계층에 전달해야 한다.**

### Related Knowledge
- Concepts: [[agent-cli-contract]]
- Patterns: [[write-validation-matches-read-semantics]]
- **Anti-Patterns**: [[검증 계층 위의 토큰 전처리]] (신규 후보)

## Case 2: 모니터 뷰어 — "서버·DB 없음" 원칙 안에서 읽기 전용 localhost 뷰어의 경계

### Grounding
- Git Context: `hash:2d5af9a` (llm-wiki monitor 구현), 후속 `d709748`·`fac5062` (종결 컬럼·상세 보기)
- Evidence: plan.md 1.4(파일이 정본이면 서버는 레포를 읽기전용으로 색인하는 방향)·6.6(칸반 웹 뷰어에 탭 하나로 붙는다)이 예약한 자리. 설계 리뷰 판정: [확정] 항목과 무충돌(1.2가 금지하는 건 에이전트의 의존 사슬이지 사람용 뷰어가 아님)
- Confidence: 5/5

### Design Decision
사람용 실시간 보드 뷰어를 `llm-wiki monitor`(127.0.0.1, Node 내장 http, 0의존성)로 만들되: 카드 정본은 파일, **쓰는 건 CLI뿐**(모든 비-GET은 405), 서버는 상태를 남기지 않음. 갱신은 **2초 폴링**(fetch 2회)으로.

### Alternatives Considered
- Option A: fs.watch + SSE 푸시 — 기각. Windows fs.watch는 junction에서 불안정하다는 wait 구현 교훈(2026-09-12)의 재수입이고, SSE는 두 번째 연결 프로토콜이라 배관이 먼저다(작업 원칙 1).
- Option B: board --html 정적 갱신 유지 — 사용자가 직접 폐지 판단("텍스트면 LLM엔 충분, 사람용은 실시간 모니터로"). 유도물은 갱신을 강제하는 게 없으면 썩는다(3.7 원칙 2) — 정적 스냅샷은 썩은 유도물의 표본.
- Selected: 폴링. localhost 2초 지연은 사람이 보기에 충분하고 코드가 가장 작다.

### Decision Code
```js
server.listen(port, '127.0.0.1', () => {
  console.log(`http://127.0.0.1:${server.address().port}`); // stdout 첫 줄 = URL 계약
});
// 페이지: setInterval(tick, 2000); tick()은 fetch('/api/board') + fetch('/api/activity')
```

### Analysis
- Context: stdout 첫 줄이 URL 계약이라 monitor는 bin의 auto-update 트리거 목록에서 제외(wait 제외와 같은 이유 — 배너가 첫 줄을 밀어내면 계약이 깨진다). `--port 0`(임시 포트)으로 테스트가 포트 충돌 없이 서버를 띄운다.
- **Trade-offs**: 실시간성 2초 지연 ↔ 코드 단순성·Windows 안전성. 페이지 DOM은 textContent 바인딩만(카드 제목·질문은 에이전트가 쓴 문자열 — innerHTML 금지).
- Reversibility: High (읽기 전용이라 삭제해도 정본 무손상)

### Related Knowledge
- Concepts: [[agent-cli-contract]] (stdout 첫 줄 계약·auto-update 트리거 제외 계열)
- Patterns: [[question-timing-follows-answerability]] (아침의 사람이 한 화면으로 읽는다는 지향의 연장)

## Case 3: 전역 llm-wiki는 레지스트리 재설치본이다 — npm link 시효 만료, 검증 경로 재확립

### Grounding
- Git Context: `hash:30fc55a`(0.3.0 게시 후 재설치) 이후 상태, 오늘 실측
- Evidence: 폐지 커밋 직후 전역 `llm-wiki board --html`이 **옛 동작을 그대로 수행**("Board written: …board.html" exit 0)하는 동안 `node bin/llm-wiki.js board --html`은 "모르는 플래그" exit 1. 두 경로가 다른 코드를 실행 중
- Confidence: 5/5

### Discovery
과거(2026-09-10~12)엔 전역 llm-wiki가 이 레포 작업 나무로 npm link돼 미커밋 변경이 즉시 기계 전역에 반영됐다. **0.3.0 게시 후 레지스트리 재설치로 그 link는 사라졌다** — 전역 명령은 이제 게시된 버전만 따라간다.

### Analysis
- Why non-obvious: 메모리가 "link 상태"를 계속 주장하고 있어서, 전역 명령이 옛 동작을 내는 것을 "내 수정이 안 먹혔다"로 오독하기 쉽다(실제로는 수정이 잘 됐고 전역이 옛본이다).
- Impact: 도그푸딩 개발 중 검증은 반드시 `node bin/llm-wiki.js` 직접 실행. 사용자 레포 반영은 publish + npm update 경로뿐.
- Action taken: 메모리 정정(machine-gpu-qmd-state). 다시 link하려면 사용자 지시 필요.

### Related Knowledge
- Concepts: [[npm-scoped-publishing]]
- Patterns: [[always-merge-exact-matching]]은 무관 — 링크 없음

## Case 4: 백그라운드 작업 정지가 Windows에서 node 자식을 안 죽인다 — 고아 서버의 포트 점유

### Grounding
- Git Context: `hash:d709748` 작업 중 실측(재기동 시도 때 발견)
- Evidence: 백그라운드로 띄운 `node bin/llm-wiki.js monitor`를 작업 정지로 멈춘 뒤 재기동하자 새 서버가 즉시 죽으며 출력: `✗ 포트 4747가 이미 쓰이고 있다 — --port <다른 번호>로 바꿔라.` netstat으로 PID 확인 → node.exe가 살아 있었음(셸만 죽고 자식 생존)
- Confidence: 5/5

### Error
```
✗ 포트 4747가 이미 쓰이고 있다 — --port <다른 번호>로 바꿔라.
```
(설계해둔 EADDRINUSE 처리 메시지가 실전에서 정상 작동한 첫 사례이기도 하다 — server.on('error') → exit 1.)

### Environment Context
- Packages: Windows 10 (10.0.26200), Git Bash, ZCode 백그라운드 작업(TaskStop)
- Migration Issue: No

### Fix Code
```bash
netstat -ano | grep ":4747" | grep LISTEN   # PID 확인
tasklist //FI "PID eq <PID>"                 # node.exe인지 확인 후
taskkill //PID <PID> //F                     # 자식까지 강제
```

### Analysis
- Root cause: 작업 정지가 프로세스 트리가 아니라 래퍼 셸만 종료시켰다. Windows에선 프로세스 그룹 시그널(POSIX 개념)이 없어 부모 사망이 자식에 전파되지 않는다.
- Why it failed: "정지 성공" 피드백과 실제 생존이 어긋난다 — 사용자는 죽었다고 믿은 서버의 옛 화면을 계속 보게 된다(이 날 모니터가 옛 코드를 보여준 이유이기도 했다).
- How it was fixed: 고아 kill + `netstat`으로 포트 확인 후 재기동하는 순서를 습관화. 코드 쪽에서는 EADDRINUSE 메시지가 이미 정확히 안내하고 있었음.

### Related Knowledge
- Concepts: [[agent-cli-contract]] (오류 메시지가 다음 행동을 지시하는 계열)
- Patterns: [[flush-before-exit]]과 같은 Windows 프로세스 경계 계열
- **Anti-Patterns**: [[정지 피드백만 믿고 포트를 안 확인하는 재기동]] (신규 후보)

## Case 5: 페이지(JS) 런타임 오류는 노드 테스트가 못 잡는다 — sed 치환 스코프 사고, 브라우저 실측이 게이트

### Grounding
- Git Context: `hash:fac5062` (수습 포함)
- Evidence: 카드 빌더 일괄 치환(`sed s/el('div', 'card')/cardEl(c.title)/`)이 종결 컬럼의 맵 변수 `t`까지 `c.title`로 바꿈. 노드 테스트 55/55 통과(페이지 JS는 문자열일 뿐 실행 안 됨). 브라우저(IAB) 실측에서만 요약 줄에 `연결 끊김 — 서버가 죽었거나 보드를 읽을 수 없다 (c is not defined)` 로 노출 — ReferenceError가 tick()의 catch에 잡힌 것
- Confidence: 5/5

### Error
```
c is not defined
```

### Environment Context
- Packages: llm-wiki monitor 페이지(임베디드 HTML+JS), Node --test는 서버 API만 검증
- Migration Issue: No

### Fix Code
```js
// 종결 컬럼 맵은 파라미터가 t다 — 일괄 치환의 전제(전부 c)가 틀렸다
...(view.terminalRecent || []).map(t => {
  const card = cardEl(t.title);   // cardEl(c.title) → cardEl(t.title)
```

### Analysis
- Root cause: 네 개의 동일 패턴 중 세 개는 `c`, 하나는 `t` — 정규식 일괄 치환은 스코프를 모른다.
- Why it failed: 서버 사이드 테스트(/api 응답·페이지 **문자열** 골격 포함)는 클라이언트 JS 실행을 커버하지 않는다. renderBoard가 도중에 던지면 tick()의 catch가 "연결 끊김"으로 뭉뚱그려져 서버 결함으로도 위장한다.
- How it was fixed: 변수 수정 + **모니터 페이지 변경의 게이트는 브라우저 실측**임을 카드 Result와 메모리에 명시.

### Related Knowledge
- Concepts: [[agent-cli-contract]] (오류가 다른 계층 결함으로 위장 — 계약 표면의 정확성)

## Case 6: 카드 파서는 Goal·AC를 센티넬 특별 취급한다 — sections Map엔 나머지만 들어 있다

### Grounding
- Git Context: `hash:fac5062` (/api/card 구현 중 발견)
- Evidence: 디버그 실행 `sections keys: [ 'Plan', 'Notes', 'Handoff', 'Result' ]` — Goal·AC 없음. lib/kanban.js parseBody: 반환형 `{ goal, ac: [{checked, idx, text}], sections: Map<name, bodyText> }`, goal은 `<!-- kanban:goal:begin/end -->` 사이, AC는 `<!-- kanban:ac:begin/end -->` 사이에서 정규식 추출
- Confidence: 5/5

### Discovery
카드 파일의 `## Goal`·`## Acceptance Criteria`는 센티넬 블록으로 파싱돼 `card.goal`(문자열)과 `card.ac`(구조화 배열)에 들어가고, `card.sections` Map은 **센티넬을 제거한 나머지 섹션**(Plan/Notes/Handoff/Result·기타)만 담는다. 본문 전체를 내보내는 코드는 `sections.get('Goal')`로 접근하면 undefined를 받는다.

### Analysis
- Why non-obvious: 파일에는 `## Goal` 헤더가 그대로 있어 "헤더=섹션"이라는 자연스러운 모델이 틀리지 않아 보인다. 왕복 보존(serializeCard가 센티넬을 재생성)을 위해 파서가 특별 취급하는 것이다.
- Impact: 모니터 /api/card는 goal·ac를 **파일 순서(Goal → AC → 나머지)로 재합성**해 반환한다. AC 표시는 `- [x] #N 텍스트` 형식으로 재구성(체크 상태 보존).
- Action taken: 재합성 구현 + 회귀(sections.Goal·Result 단언).

### Related Knowledge
- Concepts: [[write-validation-matches-read-semantics]] (왕복 보존 계열)
- Patterns: [[always-merge-exact-matching]]과 무관 — 파서 내부 계약
